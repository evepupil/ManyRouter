# New API 同步与核对模块设计

> 模块定位：通过 New API 现有管理接口应用单站线路方案，重新读取并确认真实状态
> 对应代码：`internal/application/reconciliation`、`internal/adapters/gateway/newapi`、`internal/jobs`、`internal/adapters/storage/postgres`
> 所属里程碑：[M0 - 跑通单站供应商接入闭环](../roadmap.md#m0)、[M1 - 跑通多站人工运营闭环](../roadmap.md#m1)
> 当前状态：已完成
> 最近更新时间：2026-09-05

## 1. 职责与边界

本模块负责：

- 检查 New API 状态、版本和 M0 所需能力。
- 读取受管渠道和分组倍率，转换成统一实际状态。
- 比较期望状态与实际状态，形成逐项变更计划。
- 依次应用分组倍率、渠道配置和渠道状态。
- 执行渠道连通测试，重新读取并核对所有关键字段。
- 保存实际编号绑定、操作结果、配置偏差、审计和重试状态。
- 使用 PostgreSQL 持久任务恢复进程退出前未完成的工作。

本模块不负责：

- 直接访问 New API 业务主库。
- 修改没有受管标记或绑定关系的渠道和分组。
- 在用户模型请求中实时访问 ManyRouter。
- 管理 New API 用户、用户 API Key 和余额。
- 在 M0 修改 New API 源码或转发链。

## 2. New API M0 契约

当前适配基线是官方提交 `0ed497f0` 加本地 CodeGraph 元数据提交。M0 使用现有接口：

| 能力 | New API 接口 | 说明 |
|---|---|---|
| 状态与版本 | `GET /api/status` | 无写入，用于记录版本信息 |
| 渠道列表 | `GET /api/channel/` | 管理身份；分页读取，不返回渠道密钥 |
| 创建渠道 | `POST /api/channel/` | 管理身份；创建观察状态渠道 |
| 更新渠道 | `PUT /api/channel/` | 管理身份；更新受管渠道配置 |
| 测试渠道 | `GET /api/channel/test/{id}` | 管理身份；验证真实上游连通性 |
| 更新状态 | `POST /api/channel/{id}/status` | 管理身份；请求体提供目标状态 |
| 读取设置 | `GET /api/option/` | root 身份；读取完整 `GroupRatio` 和 `UserUsableGroups` |
| 更新设置 | `PUT /api/option/` | root 身份；更新分组倍率和用户可选分组 |

现有管理接口接受 `Authorization: Bearer <访问令牌>`。渠道写入可以使用具备相应权限的管理身份；修改 `GroupRatio` 当前需要 root 权限。该高权限凭证只用于 M0 业务验证，M4 切换到窄权限整批端点。

`v1.0.0-rc.20` 等旧版 New API 还要求 `New-Api-User: 1`。M0 只接入初始化时创建的首个 root 账号，因此适配层统一补发该请求头；新版会忽略它。若站点的 root 账号编号不是 `1`，当前版本会在只读预检时停止，留到后续站点配置能力中开放编号设置。

## 3. 统一网关能力

应用层只依赖以下能力，不接触 New API JSON 字段：

- `Probe`：读取版本和可用状态。
- `ReadActualState`：读取受管渠道、分组倍率和绑定信息。
- `MergeGroupRatio`：只修改目标受管分组，保留所有非受管分组。
- `MergeUserUsableGroups`：按展示意图增加或移除目标专属分组，保留其他用户分组及说明。
- `CreateChannel`：创建带稳定受管标签的观察渠道。
- `UpdateChannel`：更新已经确认绑定的受管渠道。
- `TestChannel`：调用 New API 的真实渠道测试。
- `SetChannelEnabled`：启用或人工停用受管渠道。

每个调用设置独立超时，限制响应体大小，并同时检查 HTTP 状态和响应中的 `success`。外部错误只保存清洗后的错误码与摘要。

## 4. 同步顺序

```text
领取线路版本
      │
      ▼
检查站点与鉴权
      │
      ▼
读取渠道和完整分组倍率
      │
      ▼
按受管标识定位渠道
      │
      ▼
合并并更新专属分组倍率与用户入口权限
      │
      ▼
创建缺失渠道 / 更新已绑定渠道
      │
      ▼
重新读取并绑定实际渠道编号
      │
      ▼
执行真实渠道测试
      │
      ▼
测试通过后启用渠道
      │
      ▼
再次读取并逐字段核对
      │
      ├─ 一致：保存确认版本和审计
      └─ 有差异：保存偏差并重试或等待人工处理
```

先更新分组倍率可以保证渠道启用时已经存在有效价格。任何步骤失败都记录已完成写入，New API 可能处于部分更新状态；ManyRouter 不执行破坏性回滚或删除未知资源。

## 5. 差异与所有权规则

- 已保存的 New API 渠道编号和受管标签都匹配时才允许更新。
- 没有编号绑定时按稳定标签查找；找到一个则绑定，找不到才创建。
- 相同标签找到多个渠道时记录 `managed_resource_conflict` 并停止。
- 编号指向的渠道标签不匹配时记录 `binding_mismatch` 并停止。
- 读取和写回 `GroupRatio` 时保留全部非目标键。
- 读取和写回 `UserUsableGroups` 时保留全部非目标分组及原说明。
- 同步只增加或修改当前受管分组键，M0 不自动删除分组键。
- New API 中的人工停用视为安全锁。普通自动同步只记录 `manual_locked`，需要显式恢复动作才能重新启用。
- 首次创建固定 Auto 前先读取完整实际状态；短码只要已存在于 `GroupRatio`、`UserUsableGroups` 或任一渠道的分组集合中，就视为外部资源冲突并拒绝保存策略，避免覆盖人工组。
- 已有策略不重复执行首次占用检查。同步继续使用策略记录中保存的组键，因此升级前的 `mr_a_...` 当前策略、旧价格和后续线路保持同一身份。

## 6. 幂等、未知结果与并发

- 每次同步操作使用稳定 UUID，重试沿用原操作编号。
- 同一站点使用 PostgreSQL 事务锁和 River 队列限制为一个写任务。
- 每个步骤有唯一键，同一操作已经确认的步骤不会重复发送。
- 创建渠道请求超时属于结果未知。任务进入 `uncertain`，等待后先重新读取受管标签，禁止立即再次创建。
- 更新倍率或渠道请求超时也先重新读取；实际状态已一致时直接确认该步骤。
- 明确的校验错误和权限错误等待人工处理；网络失败、超时和服务端临时错误按退避策略重试。
- 重复触发同一线路版本只返回现有同步操作。

New API 现有创建接口没有服务端幂等键。M0 依靠单站串行、稳定标签、结果未知先读取和重复标签冲突保护满足日常重复同步。网络分区下的绝对原子幂等由 M4 整批端点解决。

## 7. 分组倍率更新保护

New API 当前把全部分组倍率保存在一份 `GroupRatio` 配置中。M0 每次更新按以下方式处理：

1. 读取完整配置并解析为键值集合。
2. 复制集合，只替换当前受管分组的倍率。
3. 规范化排序后提交完整配置。
4. 重新读取，确认目标倍率正确且原有非受管键仍存在。
5. 发现非受管键丢失时立即标记高风险偏差并停止后续启用。

M0 要求一个站点只有 ManyRouter 单实例执行自动写入。外部 root 管理员同时修改倍率可能产生竞争，运营规范要求同步期间避免并发修改；M4 的窄权限整批端点消除此限制。

New API 还允许按用户分组配置特殊的可用分组增删规则。M0 写入全站用户可用分组，真实验收账号所在用户分组不得另行移除该专属分组；M1 保持这些非受管特殊规则，并在验收时核对代表用户的实际入口权限，不在本期新增用户分组规则编辑器。关闭入口会使已有该组密钥的后续请求被拒绝。

## 8. 任务与持久状态

同步操作保存：

- 操作编号、站点、线路版本和触发原因。
- `pending`、`running`、`uncertain`、`succeeded`、`retryable_failed`、`manual_required` 状态。
- 当前步骤、尝试次数、下次重试时间和最近错误分类。
- 创建、开始、最近尝试和完成时间。

逐步结果保存步骤名、前后摘要、结果和时间，不保存密钥或完整外部响应。River 只负责领取与重试，所有业务判断由应用层完成。

## 9. 核对标准

以下条件同时成立才确认线路版本：

- 受管标签只对应一个 New API 渠道。
- 实际渠道编号已经保存绑定。
- 地址、协议、模型、模型映射、分组、优先级和权重与期望一致。
- 专属分组倍率与期望十进制值一致。
- 渠道测试成功，渠道处于启用状态。
- 非受管分组和渠道未被同步操作修改。

创建或更新接口返回成功只能推进到下一步骤，不能直接把线路版本标记为确认。

旧版 New API 创建渠道后不会立即刷新内存渠道表。首次渠道测试通过后，ManyRouter 会对尚未确认的渠道发送一次同配置更新，让 New API 通过自己的更新流程刷新缓存，再执行启用和最终核对。该动作不会用于已经确认后被人工停用的渠道。

## 10. 错误分类

| 分类 | 示例 | 处理 |
|---|---|---|
| 配置错误 | 地址、模型或倍率非法 | 停止并返回运营人员修改 |
| 鉴权错误 | 管理令牌无效或权限不足 | 停止并要求更新站点凭证 |
| 兼容错误 | 接口或字段行为不满足基线 | 站点进入只读，等待兼容处理 |
| 临时错误 | 超时、连接失败、HTTP 429、服务端临时失败 | 保存状态并退避重试 |
| 结果未知 | 写请求超时或连接中断 | 等待后先读取核对 |
| 所有权冲突 | 重复标签、绑定错位 | 停止自动修改并人工处理 |
| 人工安全锁 | 实际渠道被人工停用 | 保持停用并等待显式恢复 |

HTTP 429 表示 New API 当前触发限流，适配器将其归为 `retryable`。最终重读遇到 429 时保留整站未确认状态并安排退避重试，不进入 `manual_required`；鉴权失败、字段不兼容等需要运营处理的 4xx 响应继续按原分类处理。

## 13. M1 扩充设计

### 13.1 输入与实现边界

接收[单站线路方案](./单站线路方案.md)的完整站点快照，执行[站点与供应商接入](./站点与供应商接入.md)的编辑、启停与换密钥意图，以及[人工策略管理](./人工策略管理.md)、[稳定价格管理](./稳定价格管理.md)的成员与售价。继续调用现有 New API HTTP 管理接口。

应用层按领取操作、规划变更、逐资源执行、最终核对拆分文件；网关适配层扩展多分组写入和真实管理账号编号，存储层负责状态事务和锁，River 只负责调度。M0 单关系执行保留兼容分支，M1 完整站点执行由独立文件承载。

### 13.2 同站串行与旧任务

- River 允许多个工作任务并行，保留每站一个会话级数据库锁。不同站点独立取得锁与执行，同一站点只允许一个写任务。
- 锁键沿用 `hashtextextended(siteID::text, 1)`；业务生成计划使用相同键的事务锁。同步持有专用连接上的会话锁，外部请求不放进长时间业务事务。
- 运营发布、重复请求和旧接入入口使用快速锁；锁已占用时立即返回配置处理中，等待请求不会长期占用数据库连接。
- 先读取操作定位站点，取得锁后重新读取站点、最新计划引用、操作状态、资源绑定和凭证；不得执行锁前读到的旧数据。
- 过期计划记为 `superseded` 并终止写入。未知结果的旧操作可以先只读核对其影响，随后由最新计划纠正；不允许借重试之名发送旧凭证或旧状态。
- 任务重领和显式重试均通过同一检查；已完成任务返回已保存结果，不重新创建渠道。
- 释放锁失败须丢弃对应连接，防止持锁连接归还连接池后长期阻塞该站。

共享站点锁保证正常执行期间的计划发布顺序。现有 New API 接口缺少服务端版本校验，网络超时后的延迟写入无法获得绝对排序保证：必须先核对，再以最新计划修复；M4 的服务端整批端点进一步收紧此边界。

### 13.3 完整站点执行顺序

1. 只读检查权限、兼容性、所有受管标签和绑定，读取所有渠道、完整倍率及用户入口权限。
2. 建立非受管配置基线，计算按稳定身份列出的变更；重复标签或绑定冲突先停止该操作，避免已知冲突后继续写入。
3. 先执行明确下线：停用目标渠道，移除失效 Auto 成员，并核对结果。下线无需供应商凭证解密或上游测试，不因上游故障阻塞。
4. 合并本次全部受管专属组与 Auto 的目标价格；保留其他配置，重读确认价格后才允许新增流量。
5. 逐渠道创建观察资源或更新已绑定配置，写入完整分组集合；新渠道、恢复及涉及地址、模型或凭证的修改执行必要测试。
6. 只有最新目标要求启用且无人工锁时才启用。原先停用的渠道更换凭证后保持停用，显式恢复指令仅对指定关系和本计划有效。
7. 目标资源准备完成后合并用户可选分组并重读；实际返回中校验受管目标和非受管基线。
8. 逐资源保存确认结果；全部目标一致时，事务内确认整站线路版本与同步操作。

计费基准检查放在明确下线之后。基准缺失或变化时，先前已经确认的停用保持有效，随后停止价格修改与新增启用，并保留整站未完成结果；实际渠道停用已足以阻止其通过旧 Auto 成员关系继续接收流量。

M1 保持每关系一个渠道，渠道所属全部分组以集合比较，不能只比较一个专属组。所有 Auto 成员归属由期望快照给出，同步模块不计算评分或自行补选供应商。步骤身份使用“操作 + 资源稳定身份 + 动作”，避免多个渠道共享同一条步骤记录。

#### 渠道分组字段容量

真实验收确认 New API 的渠道 `group` 字段最多容纳 64 个字符，字段内容是该渠道全部分组用逗号连接后的字符串。既有专属组键长 37 个字符，继续保留以维持已有渠道、价格和用户 Key 的稳定身份；若五种 Auto 继续使用原 37 字符键，完整字符串会超限。

M1 将五种固定 Auto 映射为单个 New API 实例内稳定的 4 字符短码：最低价 `mrap`、低延迟 `mral`、高 SLA `mras`、高质量 `mraq`、均衡 `mrab`。ManyRouter 以站点与策略类型确定业务身份，线路写入和核对渠道时使用短码。同一渠道同时加入 1 个专属组和全部 5 个固定 Auto 时，总长度为 `37 + 5 × 4 + 5 个逗号 = 62`，给定当前固定集合时不会超过上限。

短码可以在不同 New API 实例复用，因为每个实例拥有各自的渠道、倍率和用户可选分组。迁移 `00003_m1_site_identity.sql` 阻止同一规范化 New API 地址登记到两个站点；地址别名仍无法自动识别，运营人员必须确认每个站点连接独立实例。同一实例不能承载两个复用短码的 ManyRouter 站点。

升级前的 `mr_a_...` 当前策略继续使用原组键及原价格，旧线路快照也继续可读和校验；首次创建的新策略使用短码。当前通过固定类型集合和单元测试锁定 62 字符上限，用户自定义 Auto 需要另行加入容量预算和超限处理。本次修复期间仅对隔离验收库中由失败验收产生的记录执行过一次性迁移，正常产品数据和后续验收不自动改写旧策略。

### 13.4 启停与人工锁

| 当前情况 | 目标 | 处理 |
|---|---|---|
| 实际渠道不存在 | 停用 | 不创建渠道；确认不存在，保留投放身份 |
| 实际渠道启用 | 停用 | 直接停用并重读；无需先测试上游 |
| ManyRouter 已确认停用 | 启用 | 当前计划明确恢复后，测试通过再启用 |
| New API 人工停用，上一确认目标为启用 | 启用 | 记录人工锁；没有本计划显式恢复指令就保持停用 |
| 人工锁定渠道 | 换密钥或改资料 | 不自动启用；需要写入的受锁操作保留待处理结果 |
| 已启用且配置无变化 | 启用 | 重读核对后复用确认，不制造无必要重写 |

渠道记录保存最近确认的目标启用状态，区分 ManyRouter 下线与 New API 人工停用。M0 已确认渠道升级时可回填为启用，未确认渠道保持未知，不误判为已人工锁定。

### 13.5 凭证写入与未知结果

New API 渠道查询不会返回密钥，所以“可读渠道字段一致”不足以确认密钥已经更新。每个受管渠道额外保存最近确认的凭证身份与版本；与目标不同则强制写入密钥，写入成功后测试并核对其他字段，完成后才更新确认版本。

目标凭证从各资源快照引用读取，撤销或缺失时明确失败；不得悄悄换成数据库当前版本，也不得自动回退旧密钥。站点管理令牌独立读取当前有效版本，不从历史线路快照恢复。

密钥更新请求超时后，仅测试成功无法证明使用了新密钥，因为旧密钥可能仍然有效。任务先重读确认资源身份与可读配置；确认计划仍是最新后，对相同渠道重发同一目标凭证更新，取得明确成功并测试后再记录版本。任何结果未知都不撤销旧密钥，也不把整个轮换显示为完成。

### 13.6 部分成功、价格与确认事务

- 一个站点对应一个线路同步操作，批量投放在上层聚合逐站结果；一个站点失败不取消其他站点任务。
- 同站逐资源写入可能部分成功。明确记录每个渠道与分组的结果，失败时保留已经生效的状态，停止依赖失败步骤的后续启用；重试从实际状态重新计算差异。
- 渠道的外部编号、最近确认凭证和资源配置确认以短事务保存；整站成功只在最终重读全部一致后提交，不提前给其他未完成资源写成功状态。
- 改价和成员变化分别核对，各站独立更新价格生效记录。单站局部失败时不能把整份价格版本标记成全部生效，也不能改写另一个站点的结果。
- 更新整份倍率或入口权限配置时，读取后只替换本次受管键，提交后比较所有非受管键和值。外部管理员并发编辑仍存在竞争，M1 保留单站自动写入方和同步期间避免外部编辑的操作约束。
- 按用户分组另设的 New API 规则不在本期修改范围；全站配置完成与代表用户实际入口权限分别验证。

价格引用同时保存 New API 管理端暴露的计费配置和声明版本摘要，同步前与最终确认前各核对一次。只提取模型、输出、缓存、图像、音频、用户分组特价等计费白名单，排除本模块自己维护的分组倍率与入口权限，也不保存其他可能含凭证的设置。摘要只覆盖已暴露配置与声明版本；源码内默认价格及实际账单仍需真实消费记录验收。

受管倍率写入后会重读全部倍率并再次核对计费摘要；两者一致便独立保存价格成功核对事实。后续渠道或入口操作失败时，整站计划仍为失败，已经核对的价格结果作为部分成功保留。

整站确认要求启用渠道配置、完整有效分组成员、价格、入口权限及目标启停一致。普通停用目标以确认渠道停用或不存在为准，地址与模型等停用后不影响调用的配置可在恢复前补齐；停用渠道涉及凭证轮换时仍须取得新密钥写入证明。启用目标需有有效凭证和相应测试结果，人工锁、未知写入或任一目标偏差均阻止整站确认。

### 13.7 验证方式

- 保留 M0 真实进程合同测试和单关系历史快照回归，确认旧渠道、分组与凭证行为不回退。
- 应用层单测覆盖两供应商加 Auto 的整站同步、纯密钥变化、停用无测试、显式恢复、人工锁与逐资源失败。
- PostgreSQL 集成测试覆盖同站互斥、双站并行、持锁后重读、过期任务终止、任务重领和锁释放异常。
- HTTP 合同测试覆盖多分组集合、Auto 价格及入口权限、非默认管理账号编号、密钥更新未知结果和非受管配置保护。
- 应用测试覆盖首次固定 Auto 短码在倍率、用户入口或渠道成员中被占用时拒绝保存，以及已有策略跳过首次占用检查。
- PostgreSQL 集成测试覆盖相同规范化 New API 地址触发唯一约束，并覆盖旧 `mr_a_...` 当前策略沿用原组键与原价格。
- 领域与线路测试覆盖 New API 渠道 `group` 的 64 字符边界：既有专属组键不变，五种固定 Auto 各使用固定 4 字符短码，最坏组合长度为 62；旧 `mr_a_...` 线路快照继续可读。
- 双站验收按[统一验收口径](../需求设计.md#m1-acceptance-scope)使用 3～5 个独立供应商记录，允许复制同一真实上游的地址、密钥和模型，但记录、投放关系、渠道及分组必须独立。
- 两个目标必须是独立运行、配置与业务数据库隔离的 New API 实例，不能复制同一地址或用同一实例的不同别名代替。通过真实调用验证独立定价与入口权限、单站同步失败另一站完成、凭证逐站确认和旧任务无法覆盖新计划。

验收报告分别记录供应商记录数和真实上游数，并标明复制来源。关闭某条受管线路或使一个站点管理接口失败，可以验证控制和同步隔离；同一真实上游的复制记录无法证明不同厂商之间的独立故障容错、采购成本差异或模型能力差异，这些能力留待后续运营验证。

首轮真实验收在 `manual_strategies` 阶段失败：将人工策略写入渠道后，数据库返回 `SQLSTATE 22001`。该结果确认了完整分组字符串的 64 字符边界，并推动固定 Auto 改用短码；该故障已在第二轮验收中跨过。

第二轮真实验收确认短码修复已经通过 `manual_strategies`，两个独立 New API 实例上的专属组与 Auto 组调用成功，两个实例的实际用量均有增长，入口关闭后调用被拒绝、重新开放后恢复调用。当时在 `price_and_membership_isolation` 的 `final_read` 阶段遇到 HTTP 429，被误记为 `manual_required`。适配器已把 429 改为 `retryable`，最终复验完成该场景和后续全部检查。

- 已实现完整站点资源执行、渠道加入多个分组、受管分组价格与入口权限合并、逐资源确认和整站最终核对。
- 已实现首次固定 Auto 的真实站短码占用检查、同一规范化 New API 地址唯一约束，以及旧 `mr_a_...` 当前策略和价格的兼容路径。
- 已实现供应商渠道测试错误的密钥清洗；上游错误即使包含完整密钥，也不会写入同步步骤、错误摘要或控制台响应。
- 队列允许四个任务并行，同一站点仍由数据库锁串行处理；计划发布使用相同锁，锁后重读会拦截过期计划。
- 已实现先下线再处理其他变更，上游凭证缺失时仍可停用；已有停用渠道轮换凭证后保持停用。
- 已实现凭证版本差异强制下发，未知写入重试不会仅凭旧密钥仍可测试成功就确认新版本；全部已有渠道确认后才提升供应商候选版本。
- 已支持实际管理账号编号和计费基准摘要检查；模型价格或 New API 版本变化会阻止继续启用与整站确认。
- 领域、同步、网关单测和并发检测已通过；真实 PostgreSQL 已验证逐站候选提升、停用渠道确认、同站互斥、连接池不被等待锁耗尽、价格部分成功和不同站点独立执行。
- [最终真实验收](../验收/M1-真实验收-2026-09-05.json)全部通过：3 个独立供应商记录来自 1 个真实上游，运行在 2 个独立 New API 实例；各站 2 条临时 Key 完成专属和 Auto 调用，两站均确认实际用量增长。
- 不同 Auto 成员与售价、专属和 Auto 入口关闭返回 403 及重新开放、历史恢复、单站同步失败隔离及恢复均通过。两站各 2 条旧操作进入已替代状态；重复同步复用已有渠道，ManyRouter 停止后两站继续调用。
- 真实站渠道总数保持 10 条，其中 3 条本次受管渠道已逐项核对；原有其他渠道、组入口和网关选项未被修改。4 条临时 Key 全部删除，真实站用户 Key 数量保持 5 条，临时站点已暂停。
- 渠道分组 64 字符边界和 HTTP 429 重试分类修复完成复验，M1 同步扩充已完成。结论限于受测实例与模型的真实调用及用量，复制记录不代表多个独立厂商，特殊计费与完整价格算法仍按后续范围验证。
