# ManyRouter 需求设计

> 版本：0.2.0
> 日期：2026-09-03
> 状态：已确认
> 后续设计：[技术设计](./技术设计.md)｜[架构设计](./架构设计.md)｜[Roadmap](./roadmap.md)

## 1. 文档范围

本文只定义 ManyRouter 要解决的问题、面向谁、提供什么能力、遵循什么业务规则，以及首期如何验收。

本文不讨论具体实现方式，相关内容见[技术设计](./技术设计.md)与[架构设计](./架构设计.md)。

## 2. 一句话定义

ManyRouter 聚合多家 AI API 中转供应商，根据真实使用数据持续评估价格、延迟、可用性和模型质量，动态维护可用线路池，并通过统一且相对稳定的价格向用户提供可直选、可自动切换的 AI API 服务。

## 3. 要解决的问题

当前低价 AI API 中转市场存在以下长期问题：

- **供应商跑路**：预充值后失联、关站或停止服务，用户余额和业务同时受损。
- **模型掺水**：供应商用低规格模型冒充高规格模型，或者在用户不知情时更换实际模型。
- **可用性低**：账号池、上游余额或供应商自身容量耗尽，造成大量失败、限流和长时间不可用。
- **延迟不稳定**：同一供应商在不同模型、不同时段和不同地区的首字时间、总耗时差异很大。
- **选择成本高**：用户需要反复找站、充值、测试、切换地址，并自行承担判断失误的成本。
- **价格与质量不透明**：供应商宣传信息缺少持续、可验证的真实流量依据。

ManyRouter 的目标是把这些风险集中管理，让用户只选择价格和服务偏好，无需持续盯住每一家上游供应商。

## 4. 产品原则

- 平台不经营上游账号池，供应商自行承担账号、余额、容量和上游资源。
- 平台不依赖单一供应商，供应池的广度和动态淘汰能力共同支撑服务连续性。
- 供应商宣传资料只作参考，准入、排序、退出和恢复以平台测得的数据为准。
- 用户价格包含合理利润和风险准备，日常保持稳定。
- 上游成本出现普遍或显著变化时，平台才调整对外价格。
- 自动策略的选择结果可以变化，用户看到的产品名称、计费规则和价格保持清晰。
- 模型真实性属于准入门槛，低价不能抵消冒充模型等严重问题。
- 每次自动调整都必须可追溯，运营人员能够看到原因、时间和调整前后的结果。
- 多个站点使用同一套产品能力，禁止为单个站点长期维护独立业务分支。

## 5. 用户与使用场景

### 5.1 API 用户

API 用户希望获得统一的调用方式、稳定价格和更高的服务连续性。用户可以：

- 选择指定供应商线路。
- 选择平台提供的固定 Auto 策略。
- 配置自己的 Auto 偏好并在确认报价后使用。
- 查看模型价格、可用供应商数量、延迟、可用性和质量信息。
- 查看自己的使用记录和实际体验统计。

### 5.2 运营人员

运营人员负责接入供应商、设置价格、制定准入规则、查看异常、处理告警和管理多个站点。

### 5.3 站点经营者

同一经营主体可以建立多个定位不同的站点。每个站点可以拥有自己的品牌、域名、产品目录、利润率、用户、余额和订单，同时复用已经验证的供应商信息与基础测评结果。

## 6. 核心业务对象

### 6.1 供应商

供应商是一家可提供 AI API 能力的上游中转站。平台为每个供应商统一维护基本资料、访问凭证、模型清单、采购价格、余额、状态和历史表现。同一供应商默认在多个自营站点间共用一个上游账号与访问凭证。

### 6.2 供应商分组

每个供应商拥有一个专属分组。用户选择该分组时，表示明确选择这家供应商，价格由该供应商分组的倍率决定。

供应商可以同时加入一个或多个 Auto 策略组。退出 Auto 策略组不会自动取消其专属分组。

### 6.3 Auto 策略组

Auto 策略组包含一批符合相应标准的供应商。平台根据最新统计结果动态增加或移除成员。

每个 Auto 策略组拥有独立价格。用户通过 Auto 策略调用时，供应商切换对用户透明。

### 6.4 站点

站点是一套可独立经营的产品实例。站点拥有独立的品牌、用户资产、销售价格和可见产品，同时遵循 ManyRouter 的统一需求和兼容规则。

### 6.5 站点供应商关系

平台需要记录每个站点启用了哪些供应商、对应的供应商专属分组、实际渠道、可见状态、价格和 Auto 参与情况。同一供应商可以在不同站点采用不同的展示和策略，但供应商资料与上游凭证只维护一次。

## 7. 供应商管理需求

### 7.1 供应商录入

运营人员可以录入和维护：

- 供应商名称与内部标识。
- 服务地址与访问凭证。
- 支持的协议和模型。
- 供应商公开价格与平台确认后的采购价格。
- 当前余额、充值记录和余额更新时间。
- 适用站点、专属分组和可参加的 Auto 策略。
- 运营备注、风险记录和人工处理结果。

供应商资料在 ManyRouter 中只录入一次。运营人员选择目标站点后，平台负责在这些站点建立和维护所需的渠道、供应商专属分组、价格及策略关系，禁止要求运营人员再到各站点重复录入。

### 7.2 接入流程

供应商接入遵循以下流程：

1. 录入资料、模型和价格。
2. 选择需要接入该供应商的站点。
3. 平台在目标站点自动建立渠道、供应商专属分组和对应价格。
4. 完成连通性与基本能力检查。
5. 进行小额充值和试用。
6. 先开放供应商专属分组进行观察。
7. 达到准入标准后进入合适的 Auto 策略组。

接入一家资料完整、协议兼容的供应商，目标操作时间不超过 30 分钟。

### 7.3 资金风险

- 对供应商采用小额、多次充值。
- 根据近期消耗速度设置单家供应商的资金暴露上限。
- 定期核对供应商余额变化与平台记录的实际消耗。
- 余额低于安全值时提前告警。
- 余额耗尽、余额异常或无法核对时停止其自动流量。
- 所有充值、余额快照和对账结果必须留档。

## 8. 数据统计与测评需求

### 8.1 真实流量统计

平台持续统计每个“供应商 + 模型”组合的真实表现，至少包括：

- 请求量与有效样本量。
- 成功率、失败率和连续失败次数。
- 首字时间和请求总耗时。
- 限流、余额不足、鉴权失败、超时和其他错误分布。
- 流式响应是否正常结束。
- 输入、输出和总用量。
- 不同时段的表现变化。
- 发生供应商切换后的最终结果。

近期数据在评分中应具有更高影响，过旧数据逐步降低影响。

### 8.2 低频主动测评

真实流量不足时，平台需要通过低频主动测评补充数据，主要用于：

- 新供应商首次准入。
- 新模型首次准入。
- 长时间没有真实流量的供应商。
- 已退出 Auto 的供应商恢复评估。
- 发生异常后确认是否恢复。

主动测评数据与真实用户流量需要分别标记，运营人员可以分别查看。

### 8.3 模型真实性与质量

- 平台应定期检查供应商返回的模型是否符合其声明。
- 检查结果至少包括真实性结论、质量得分、可信度和最近检查时间。
- 模型真实性不通过时，该供应商的对应模型不能进入任何 Auto 策略。
- 严重冒充或批量替换模型时，可以停用该供应商的全部线路。
- 具体测试题、判断细节和参考答案属于平台内部信息，不向普通用户或供应商公开。
- 用户侧可以看到质量等级、可信度范围和更新时间，不显示可被针对性规避的检测细节。

### 8.4 地区差异

平台后续应支持按地区统计和展示延迟、成功率及可用性。同一供应商在不同地区可以得到不同的适用结论。

## 9. 评分需求

### 9.1 评分维度

平台从以下四个维度评价供应商：

| 维度 | 含义 |
|---|---|
| 价格 | 平台实际采购成本及近期价格稳定性 |
| 延迟 | 首字时间、总耗时及波动情况 |
| SLA | 成功率、限流情况、连续故障、恢复速度和容量稳定性 |
| 质量 | 模型真实性、能力表现及质量稳定性 |

### 9.2 硬性排除条件

出现以下情况之一时，供应商或对应模型不得参加综合评分排序：

- 模型真实性检查不通过。
- 访问凭证无效。
- 余额耗尽或确认无法继续提供服务。
- 连续失败达到停用标准。
- 存在运营人员确认的重大风险。

### 9.3 综合评分

- 通过硬性检查的供应商按照价格、延迟、SLA 和质量权重计算综合得分。
- 权重可以由平台固定策略提供，也可以由用户自行配置。
- 评分规则、准入线、退出线、最小样本量和观察时间可以由运营人员配置。
- 成员变化需要设置缓冲区，避免供应商在短时间内反复进入和退出 Auto。
- 评分变化本身不应造成用户价格频繁变化。

## 10. 分组与线路调整需求

### 10.1 专属分组

- 每个供应商始终拥有一个专属分组。
- 用户主动选择专属分组时，平台按该分组价格计费。
- 供应商普通表现下降时，可以退出 Auto，同时继续保留专属入口。
- 专属入口需要向用户展示当前风险、最近统计时间和是否推荐使用。

### 10.2 Auto 成员变化

- 达到准入线并满足观察期要求后，供应商进入对应 Auto 策略组。
- 低于退出线、近期表现恶化或余额接近安全下限时，供应商退出对应 Auto 策略组。
- Auto 成员变化后，新请求使用新的可用供应池。
- 已经开始输出内容的流式请求不承诺无感重放。
- 连接失败、首字前失败和可安全重试的普通请求，应尽量切换到其他合格供应商完成。

### 10.3 全局停用与恢复

以下情况触发全局停用：

- 模型严重冒充或供应商批量替换模型。
- 凭证失效。
- 余额耗尽。
- 连续探测和真实流量均表明服务不可用。
- 供应商关站、失联或被运营人员判定为高风险。

恢复需要连续多次检查通过。人工停用的供应商只能由运营人员恢复，自动恢复不得覆盖人工决定。

## 11. Auto 产品需求

### 11.1 固定策略

首期提供以下固定策略：

- **最低价**：在通过基本质量和可用性门槛后优先降低价格。
- **低延迟**：优先选择首字时间短、延迟波动小的供应商。
- **高 SLA**：优先选择成功率高、容量稳定、故障恢复快的供应商。
- **高质量**：优先选择真实性和能力表现更好的供应商。
- **均衡**：在价格、延迟、SLA 和质量之间保持平台设定的平衡。

### 11.2 用户自定义 Auto

- 用户可以调整价格、延迟、SLA 和质量四项占比。
- 四项占比合计必须为 100%。
- 平台根据最新有效数据立即给出预估结果和 Auto 报价。
- 用户确认报价后，可以保存策略并创建对应的 API Key。
- 自定义策略仍然受真实性、余额、连续失败等硬性门槛约束。
- 平台可以复用内容相同或足够接近的策略，用户侧体验不得因此改变。

### 11.3 Auto 报价

- Auto 报价综合考虑预计采购成本、风险准备、支付与运营成本以及平台利润。
- 报价应包含合理的成本波动空间。
- 日常供应商排名或成员变化不直接触发价格调整。
- 多家主要供应商的采购价格发生显著变化时，平台可以调整 Auto 价格。
- 价格调整需要记录原因、生效时间和调整前后的价格。
- 用户在开始使用前能够看到当前价格及最近更新时间。

## 12. 用户侧产品需求

### 12.1 API 使用

- 提供统一的 OpenAI 兼容调用入口。
- 提供统一的 Anthropic 兼容调用入口。
- 用户可以创建绑定供应商专属分组的 API Key。
- 用户可以创建绑定固定或自定义 Auto 策略的 API Key。
- Auto 内部发生供应商切换时，用户无需修改调用地址或 API Key。

### 12.2 模型与策略展示

用户至少可以查看：

- 模型名称和当前价格。
- 当前可用供应商数量。
- 可选供应商专属线路。
- 可选 Auto 策略及其价格。
- 近期 SLA、延迟区间、质量等级和统计更新时间。
- 数据不足、正在观察或近期异常等状态。

### 12.3 用户统计

登录用户可以查看与自身请求有关的统计，包括：

- 请求成功率。
- 首字时间和总耗时。
- 使用过的策略。
- 发生自动切换的次数和最终结果。
- 按模型和时间范围查看的使用趋势。

普通用户不应看到供应商密钥、余额、内部名称、详细故障原因、完整评分公式和检测题目。

## 13. 运营控制台需求

ManyRouter 需要提供一个简洁的运营控制台，至少覆盖以下工作：

### 13.1 站点配置

- 新增、编辑、启用和停用站点。
- 配置站点名称、域名、品牌信息和产品目录。
- 配置站点可见的供应商分组和 Auto 策略。
- 配置站点利润率和销售价格。
- 查看站点与兼容版本状态。
- 查看站点的供应商、渠道和分组同步状态。

### 13.2 供应商与分组

- 录入和编辑供应商。
- 查看供应商支持的模型、价格、余额和当前状态。
- 管理供应商专属分组。
- 查看供应商当前加入的 Auto 策略。
- 人工执行退出 Auto、全局停用、恢复和重新观察。
- 选择供应商适用的站点，并查看各站点的自动创建与同步结果。

### 13.3 规则配置

- 配置固定策略的四项权重。
- 配置准入线、退出线、最小样本量和观察期。
- 配置连续失败、余额和延迟告警值。
- 配置价格利润和风险准备。
- 配置主动测评频率和范围。
- 按站点决定启用哪些 Auto、允许哪些供应商参加，以及是否向用户显示供应商专属分组。
- 策略保存后自动同步到受影响的站点，并显示每个站点的执行结果。

### 13.4 监控与审计

- 查看供应商和模型的当前评分。
- 查看历史 SLA、延迟、错误、质量和价格趋势。
- 查看当前 Auto 成员及最近变化。
- 查看低余额、模型异常、连续失败和价格变化告警。
- 查看系统自动执行和人工执行的完整操作记录。
- 每次变化需要显示业务原因，禁止只显示无法理解的内部编号。

## 14. 多站点需求

### 14.1 重复部署

- 建立新站点时，可以使用同一版本的 ManyRouter 与受支持的 New API 完成部署。
- 新站点通过配置即可拥有独立域名、品牌、用户、余额、订单、价格和产品目录。
- 建立新站不得要求复制和长期维护一套独立业务代码。
- 单个站点出现故障或配置错误时，不应影响其他站点继续服务。

### 14.2 数据共享与隔离

- 同一经营主体的站点可以共享供应商基础资料、主动测评、模型真实性和基础评分。
- 同一供应商默认在多个自营站点间共用上游账号与访问凭证，余额和上游总限额按供应商整体管理。
- 各站点的用户、余额、订单、销售价格、利润和产品配置彼此隔离。
- 各站点可以根据自身定位决定是否采用某家供应商或某个 Auto 策略。
- 平台按站点分别统计请求、成本、收入、成功率和延迟，无需依靠不同上游密钥区分站点。
- 共享统计不得泄露其他站点的用户身份、请求内容、余额和订单信息。

### 14.3 多品牌展示

- 不同站点可以分别定位为透明选站、低价、低延迟、高 SLA、高质量或综合服务。
- 站点只展示自身允许公开的产品和统计。
- 默认不公开完整供应商池、内部评分细节和真实路由关系。
- 明确定位为透明选站的站点可以展示经过运营确认的供应商信息。

## 15. New API 兼容需求

- ManyRouter 需要声明最低支持的 New API 版本。
- 每个 ManyRouter 版本需要列出已经完成验证的 New API 版本范围。
- 安装或启动时应能识别当前 New API 是否处于支持范围。
- 未经验证的版本需要明确告警，避免静默运行后产生错误计费或路由。
- New API 升级由运营人员在验证后执行，站点不自动追随上游最新版本。
- 新版 ManyRouter 应尽量继续支持已经声明兼容的 New API 版本。
- 建立第二个站点时，应能直接选择一组已经验证的版本完成部署。
- 商业发布必须遵守 New API 的许可证、署名和源码提供要求；如需闭源授权，应在发布前取得相应商业许可。

## 16. New API 用户侧扩展需求

- New API 用户侧可以增加 ManyRouter 相关页面和入口。
- 页面所需的 SLA、延迟、质量、供应商数量、Auto 策略和报价数据由 ManyRouter 提供。
- 用户沿用站点现有登录状态，不需要再次登录 ManyRouter。
- 用户侧只能获取其权限范围内的数据。
- 页面不可暴露内部访问凭证和管理权限。
- ManyRouter 提供给 New API 的能力需要保持版本可识别，并在兼容范围内维持稳定。
- ManyRouter 暂时不可用时，现有 API 调用应继续使用最后一次有效策略；统计页面可以显示数据暂时无法更新。

## 17. 信息可见范围

### 17.1 可公开信息

- 模型价格。
- Auto 策略名称和说明。
- 模型级 SLA。
- 延迟区间。
- 质量等级。
- 可用供应商数量。
- 统计时间和样本充足程度。

### 17.2 登录用户信息

- 用户自己的请求记录和统计。
- 用户保存的自定义策略。
- 用户当前使用的价格和策略。
- 与用户请求有关的自动切换结果。

### 17.3 仅运营人员可见

- 供应商访问凭证。
- 供应商真实余额与充值记录。
- 内部评分明细和检测方法。
- 完整供应商池及跨站点使用情况。
- 停用原因、风险记录和人工备注。
- 站点利润和采购成本。

## 18. 通知需求

发生以下情况时需要通知运营人员：

- 供应商余额低于安全值或余额耗尽。
- 成功率、延迟或限流情况显著恶化。
- 模型真实性或质量检查异常。
- 供应商进入或退出 Auto。
- 供应商被全局停用或恢复。
- 供应商价格发生显著变化。
- 站点与 New API 的兼容状态异常。
- 数据长时间没有更新。

通知需要包含供应商、模型、站点、原因、发生时间和建议处理动作。

## 19. 质量与安全要求

- 供应商访问凭证、站点管理凭证和用户敏感信息必须受到保护。
- 用户请求内容只在实现统计和故障判断所需的最小范围内处理。
- 普通用户无法通过页面、日志或错误信息推断完整供应商池和内部凭证。
- 自动调整失败时保留最后一次有效配置，并通知运营人员。
- 重复执行同一项调整不得产生重复分组、错误价格或相互冲突的状态。
- 统计、评分、价格和分组变化需要保留历史版本。
- 系统应支持几十家供应商、多个站点以及持续增长的请求记录。
- 用户请求过程中不依赖临时的在线评分计算结果。
- 任何计费变化都需要先生成有效价格，再用于后续请求。

## 20. 首期范围

首期需要完成：

- 支持一组明确验证过的 New API 版本。
- 接入 3～5 家供应商。
- 在 ManyRouter 中一次录入供应商，并自动同步到选定站点。
- 建立每家供应商的专属分组。
- 建立最低价、低延迟、高 SLA、高质量和均衡 Auto 策略。
- 从真实流量统计成功率、首字时间、总耗时和错误分布。
- 通过低频主动测评完成新供应商准入和异常恢复判断。
- 根据评分动态调整 Auto 成员。
- 对严重问题执行全局停用，并在达到恢复条件后恢复。
- 维护供应商分组和 Auto 策略的稳定价格。
- 提供可配置供应商、分组、规则和价格的运营控制台。
- 提供站点、供应商、渠道、分组和策略之间的对应关系及同步状态。
- 向用户展示模型价格、供应商数量、SLA、延迟和质量信息。
- 使用同一版本组合建立第二个测试站点，证明可以重复部署。

用户自由调整四项占比、更多地区测评、供应商自助录入和大规模站点管理可以在后续版本继续完善。

## 21. 暂不包含

- 平台自建上游账号池。
- 平台替供应商管理账号容量。
- 自有 GPU 机队调度。
- 对每个用户请求临时访问 ManyRouter 计算一次评分。
- 首期统一多个站点的用户账户和余额。
- 首期向普通用户公开完整供应商池和内部检测方法。
- 对流式响应已经输出的内容进行自动重放。

## 22. 首期验收标准

满足以下条件后，首期需求才可以判定完成：

1. 至少 3 家真实供应商完成接入、专属分组和 Auto 准入流程。
2. 用户可以使用供应商专属 API Key 和固定 Auto API Key 完成真实模型调用。
3. Auto 中一家供应商在首字前故障时，请求能够在允许重试的情况下切换并完成。
4. 供应商表现跌破退出线后，会在约定时间内退出对应 Auto 策略。
5. 模型真实性失败、凭证失效或余额耗尽时，会触发对应模型或供应商停用。
6. 已退出供应商恢复后，能够经过连续检查重新进入观察或 Auto。
7. 运营人员可以在控制台完成供应商、分组、规则、价格和站点配置。
8. 用户可以看到价格、可用供应商数量、SLA、延迟、质量和统计时间。
9. 所有自动调整、人工处理和价格变化都有可查询的原因与历史记录。
10. 在主要供应商价格没有显著变化时，Auto 对外价格保持稳定。
11. 使用同一套发布版本成功建立第二个测试站点，无需维护站点专属业务代码。
12. 已声明支持的 New API 版本通过完整业务验证，未经验证版本能够被识别并告警。
13. 在 ManyRouter 中新增或修改供应商后，至少两个目标站点能够自动完成渠道、专属分组和价格同步，无需进入站点后台重复配置。
14. 修改某个站点的策略后，只有受影响站点的 Auto 与供应商专属分组可见性发生相应变化，并且每个同步结果都可查询。
