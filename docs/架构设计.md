## 1. 文档范围

本文确定 ManyRouter 的系统边界、整体结构、分层、核心模块、数据归属、主要数据流、多站点协作、New API 同步方式、故障处理和扩展方向。

具体数据表、接口字段、评分公式、任务参数和页面交互进入后续模块设计。里程碑顺序和完成状态进入后续 roadmap。

## 2. 架构目标

ManyRouter 的架构需要同时满足以下目标：

- 供应商资料只维护一次，能够自动同步到多个站点。
- 站点、供应商、专属分组、Auto 策略和实际渠道之间有明确对应关系。
- 高频请求统计不经过 New API 网页接口逐页拉取。
- 所有 New API 配置变化仍通过其业务接口完成，保证缓存、关联数据和审计正确更新。
- New API 独立承担用户请求，即使 ManyRouter 暂时停止，已有调用仍能继续。
- 同一供应商默认跨站共享上游账号和密钥，同时可以按站点分别统计表现。
- 每个站点可以采用不同的品牌、供应商范围、Auto 策略、开放分组入口和销售价格。
- 增加供应商类型、评分维度、策略、站点或其他网关时，不需要改写已有核心业务。
- 新建站点能够复用已验证的 ManyRouter 与 New API 组合，减少重复配置。
- 自动调整过程可追溯、可重试、可核对、可暂停和可恢复。

## 3. 核心架构决策

| 主题 | 决策 |
|---|---|
| 平台定位 | ManyRouter 是供应商、站点、策略、价格和线路期望状态的统一管理入口 |
| 请求入口 | New API 继续处理用户鉴权、额度、计费、协议转换、选路和转发 |
| 运行关系 | ManyRouter 位于用户请求链路之外，异步读取事实并调整配置 |
| 多站管理 | 多个 ManyRouter 进程可以组成一个逻辑平台，共用平台数据库 |
| 站点执行 | 每个站点可以部署 ManyRouter 执行节点，就近读取日志并操作本地 New API |
| 日志读取 | 只读访问 New API 独立日志库中的版本化视图 |
| 配置写入 | 通过 New API HTTP 管理接口或正式窄权限端点完成 |
| 供应商录入 | 在 ManyRouter 录入一次，再自动投放到选定站点 |
| 上游凭证 | 同一供应商默认跨站共享一个账号和密钥 |
| 站点归因 | 通过站点身份、日志来源和渠道映射统计，不通过上游密钥区分 |
| 状态管理 | ManyRouter 保存期望状态，持续读取 New API 实际状态并核对差异 |
| 价格管理 | 价格版本与评分版本分离，供应商排序变化不会直接改变售价 |
| 工程形态 | ManyRouter 首期采用模块化单体，可按运行模式拆成接口节点与任务节点 |
| 用户页面 | New API 验证用户身份后访问 ManyRouter 用户侧数据 |
| 兼容方式 | 通过能力检查、适配器和真实合同测试支持一段 New API 版本范围 |

## 4. 系统总览

### 4.1 逻辑结构

```text
                         运营人员
                            │
                            ▼
                  ManyRouter 运营控制台
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│                    ManyRouter 统一平台                       │
│  站点管理  供应商管理  策略管理  统计评分  稳定价格  审计告警 │
│                                                             │
│        期望状态生成          后台任务          用户统计       │
└──────────────┬─────────────────┬──────────────────┬──────────┘
               │                 │                  │
               │                 ▼                  │
               │        ManyRouter PostgreSQL       │
               │                                    │
      ┌────────┴────────┬───────────────────────────┘
      ▼                 ▼
┌───────────┐     ┌───────────┐            更多站点
│ 站点 A    │     │ 站点 B    │                ...
│ New API   │     │ New API   │
│ 业务主库  │     │ 业务主库  │
│ 独立日志库│     │ 独立日志库│
└─────┬─────┘     └─────┬─────┘
      │                 │
      └────────┬────────┘
               ▼
       共享的上游供应商账号池
```

ManyRouter 负责管理和决策。New API 负责每一次真实用户请求。两者通过低频控制接口和只读日志连接协作。

### 4.2 物理部署结构

ManyRouter 是一个逻辑平台，可以由多个相同程序进程组成：

- **平台接口节点**：提供运营控制台、运营接口、公开统计和用户统计。
- **平台任务节点**：执行评分、价格、策略和跨站任务。
- **站点执行节点**：绑定一个或少量站点，就近读取日志库并调用 New API 管理端口。
- **一体节点**：小规模环境中同时承担上述职责。

首个站点可以使用一体节点。新增站点时，可以继续部署相同版本的 ManyRouter 与 New API；新 ManyRouter 进程加入已有平台数据库并绑定新站点。所有进程在业务上仍属于同一个 ManyRouter 平台。

站点执行节点属于优化部署方式。网络和权限条件允许时，平台任务节点也可以远程管理 New API，核心业务不依赖固定部署位置。

### 4.3 两条运行链路

系统有两条彼此隔离的链路：

```text
用户请求链路：用户 → New API → 上游供应商 → New API 计费和日志

平台控制链路：日志/探测 → ManyRouter 统计与决策 → New API 配置同步
```

控制链路中断不会直接打断用户请求链路。New API 始终使用最后一次成功应用的渠道、分组、策略和倍率。

## 5. 系统边界与数据归属

### 5.1 ManyRouter 负责

- 站点登记、连接状态和兼容结论。
- 供应商资料、上游账号、密钥、采购价格和余额。
- 供应商模型目录和模型真实性结论。
- 站点与供应商的启用关系。
- 供应商专属分组的期望配置和入口开放状态。
- 固定与自定义 Auto 策略。
- 真实流量标准化、主动测评和统计结果。
- 供应商与模型评分。
- 站点销售价格和价格版本。
- 各站点应该拥有的渠道、分组、成员和状态。
- 同步任务、实际结果、配置偏差和操作审计。
- 运营账号、权限、告警和通知。

### 5.2 New API 负责

- 用户、登录状态、API Key、余额、订单和充值。
- 用户请求鉴权、额度检查和计费。
- OpenAI、Anthropic、Gemini 等协议处理。
- 根据当前分组、优先级和权重选择渠道。
- 上游请求转发、失败重试和流式响应。
- 已应用渠道、分组倍率和 Auto 配置的运行时状态。
- 原始请求日志和 New API 自身审计。
- 用户侧 ManyRouter 页面入口和身份转发。

### 5.3 上游供应商负责

- 上游账号池、模型资源和容量。
- 供应商侧余额与限额。
- 供应商声明的模型、价格和服务信息。
- 对供应商自身服务故障的处理。

### 5.4 禁止跨越的边界

- ManyRouter 不接管 New API 用户、余额、订单和计费流水。
- ManyRouter 不连接 New API 业务主库。
- ManyRouter 不直接写入 New API 日志库。
- New API 不计算供应商评分和稳定售价。
- 用户请求不等待 ManyRouter 在线评分。
- New API 页面不持有 ManyRouter 运营凭证或供应商密钥。
- 供应商不能直接修改 ManyRouter 评分、策略成员和站点价格。

## 6. 受管资源与非受管资源

ManyRouter 只管理由平台创建或明确接管的 New API 资源。

### 6.1 受管资源

- 平台同步的供应商渠道。
- 平台创建的供应商专属分组。
- 平台创建的 Auto 分组。
- 与这些分组有关的倍率和入口开放配置。
- 平台为用户侧页面写入的兼容配置。

每项受管资源都需要记录稳定内部标识、ManyRouter 业务标识、New API 实际标识、期望版本和最后核对结果。

### 6.2 非受管资源

- 运营人员在 New API 中自行创建的普通渠道。
- 与 ManyRouter 无关的分组、模型和价格。
- New API 自身系统配置。
- 其他业务插件创建的资源。

同步过程禁止修改非受管资源。名称相同不足以证明资源由 ManyRouter 管理，必须通过已保存的绑定关系或受管标识确认。

## 7. ManyRouter 内部分层

```text
┌─────────────────────────────────────────────┐
│ 接入层                                      │
│ 运营控制台、运营接口、站点接口、用户统计接口 │
└──────────────────────┬──────────────────────┘
                       ▼
┌─────────────────────────────────────────────┐
│ 应用层                                      │
│ 接入供应商、生成统计、评估准入、报价、同步   │
└──────────────────────┬──────────────────────┘
                       ▼
┌─────────────────────────────────────────────┐
│ 业务层                                      │
│ 站点、供应商、测量、评分、策略、价格、线路   │
└──────────────────────┬──────────────────────┘
                       ▲
┌──────────────────────┴──────────────────────┐
│ 适配层                                      │
│ New API、日志源、供应商、检测、通知、存储    │
└─────────────────────────────────────────────┘
```

任务执行层从后台任务中取得工作，再调用应用层。它不直接编写评分规则、SQL 或 New API 请求。

依赖方向保持如下规则：

- 接入层和任务执行层依赖应用层。
- 应用层组合业务层提供的规则。
- 业务层只认识 ManyRouter 自己的业务对象和能力接口。
- 适配层实现业务层需要的外部能力。
- New API 版本差异、日志字段和供应商协议不能进入业务层。

## 8. 核心模块

### 8.1 站点管理

负责站点身份、品牌信息、New API 地址、日志来源、兼容状态、运行状态和站点执行节点绑定。

### 8.2 供应商管理

负责供应商资料、协议、模型、采购价格、余额、全局状态、适用站点和接入流程。

### 8.3 凭证管理

负责供应商账号和密钥的加密保存、版本、验证、轮换、逐站下发及恢复。供应商管理模块只引用凭证标识，不接触明文持久化方式。

### 8.4 站点供应商管理

负责一个供应商在一个站点中的业务状态，包括是否启用、专属分组、入口开放状态、渠道绑定、价格、Auto 资格和同步结果。

### 8.5 测量与采集

负责从各站点日志库读取请求事实、执行主动测评、规范化不同来源的数据，并保存不可修改的测量记录。

### 8.6 统计与评分

负责按时间窗口计算成功率、延迟、错误、用量和模型质量，再生成带算法版本的评分快照。

### 8.7 策略管理

负责固定 Auto、自定义 Auto、供应商专属入口与 Auto 入口开放状态、准入门槛、候选范围和各站点启用情况。

### 8.8 稳定价格

负责采购成本、利润、风险准备、站点差异和价格生效周期。评分变化只改变候选线路，不自动触发售价重算。

### 8.9 线路方案

负责把站点、供应商、评分、策略和价格合成为一份站点期望状态。它输出业务结果，不包含具体 New API 请求格式。

### 8.10 同步与核对

负责比较期望状态和 New API 实际状态，生成变更计划，执行变更，重新读取结果并记录配置偏差。

### 8.11 New API 兼容

负责版本识别、能力判断、字段转换、现有管理接口调用、正式接入端点调用和日志视图解析。

### 8.12 用户数据服务

负责向各站点提供允许公开的价格、SLA、延迟、质量、Auto 策略和用户个人统计。

### 8.13 身份、审计与通知

负责独立运营账号、站点身份、权限检查、操作历史、配置偏差告警和业务通知。

## 9. 核心业务关系

```text
供应商
├─ 一份默认上游账号与凭证
├─ 多个供应商模型
├─ 多份采购价格
└─ 多个站点供应商关系
       ├─ 一个供应商专属分组
       ├─ 一个或多个实际渠道绑定
       ├─ 多个 Auto 策略成员关系
       ├─ 一份站点销售价格
       └─ 同步状态与历史

站点
├─ 一个 New API 实例
├─ 一个独立日志来源
├─ 多个站点供应商关系
├─ 多个启用的 Auto 策略
└─ 多份线路方案与价格版本
```

### 9.1 一个供应商一个专属分组

用户视角中，一个供应商在一个站点只对应一个供应商专属分组。展示名称可以随站点品牌调整，内部标识保持稳定。

### 9.2 一个供应商可以对应多个实际渠道

同一供应商可能同时支持多种协议、不同模型集合或不同运行限制。ManyRouter 可以在一个站点内为该供应商创建多个实际渠道，它们全部归入同一个供应商专属分组。

这样可以在用户侧保持“一个供应商一个分组”，同时允许平台按模型或协议调整 Auto 成员。新增渠道拆分不会改变用户使用的专属分组和价格含义。

### 9.3 Auto 是站点级产品

Auto 策略由 ManyRouter 统一定义，各站点决定是否启用、展示名称、候选供应商范围和销售价格。相同策略在两个站点可以拥有不同成员和价格版本。

## 10. 三类状态

系统需要同时区分三类状态：

### 10.1 业务期望状态

由 ManyRouter 根据运营配置和自动决策生成，例如：

- 某站点应该启用哪些供应商。
- 应该存在什么专属分组和 Auto 分组。
- 每个渠道应该属于哪些分组。
- 哪些分组入口应该开放或关闭。
- 每个分组应该使用什么倍率。
- 某个渠道应该启用、观察或停用。

### 10.2 New API 实际状态

通过 New API 管理接口读取，包括已经存在的渠道、渠道状态、分组关系、倍率和 Auto 配置。

### 10.3 最近确认状态

ManyRouter 完成写入并重新读取后，保存经过确认的实际状态。控制台需要分别显示期望、实际和最近确认结果，避免把“已经生成计划”误报为“已经生效”。

## 11. 期望状态与核对循环

```text
运营配置或自动决策
          │
          ▼
生成站点期望状态版本
          │
          ▼
读取 New API 实际状态
          │
          ▼
计算差异和影响范围
          │
          ▼
生成带操作编号的变更计划
          │
          ▼
通过 New API 接口应用
          │
          ▼
重新读取并逐项核对
          │
     ┌────┴────┐
     ▼         ▼
  已一致     仍有差异
     │         │
 保存结果   重试或告警
```

这个循环称为“状态核对”：平台持续比较想要的配置与站点真实配置，发现差异后补齐。

### 11.1 核对规则

- 每份期望状态拥有单调递增的版本。
- 同一站点同时只应用一个版本。
- 新版本可以取代尚未开始的旧版本。
- 已开始执行的版本需要完成核对后再处理下一版本。
- 每次写操作携带稳定操作编号。
- 重复执行同一操作不能创建重复渠道或重复分组。
- 写入成功响应仅代表接口接受，重新读取一致后才标记完成。
- 同步范围只包含受管资源。

### 11.2 配置偏差处理

- New API 中缺少受管资源时，ManyRouter 自动补建。
- 受管渠道的分组、价格或普通配置被意外修改时，记录偏差并恢复期望状态。
- New API 中的人工停用视为安全锁，ManyRouter记录后暂停自动恢复。
- ManyRouter 控制台中的人工恢复可以解除安全锁。
- 无法判断来源的高风险差异只告警，等待运营人员选择采纳实际状态或恢复平台状态。
- 非受管资源保持原状。

## 12. New API 分组映射

ManyRouter 中的“分组”是完整业务对象。New API 当前没有独立分组实体，一个可用分组由多项配置共同形成：

- 渠道所属分组。
- 分组倍率。
- 用户可用分组及其请求权限。
- Auto 可用分组。
- 令牌所选分组或 Auto 列表。

New API 兼容模块负责将 ManyRouter 的完整分组配置转换成上述实际配置。业务层不直接维护多份 New API 配置映射。

### 12.1 供应商专属分组

一个站点供应商关系对应一个稳定专属分组。该供应商在站点内的所有实际渠道都加入该组。策略决定该专属入口是否开放，价格模块决定其倍率。关闭入口后，已有绑定该组的 API Key 后续请求也被拒绝；渠道仍可服务于其他已开放的 Auto。

### 12.2 固定 Auto 分组

每个启用的固定 Auto 策略在站点内对应一个共享组，例如最低价、低延迟、高 SLA、高质量和均衡。通过硬性门槛并达到该策略准入线的渠道加入对应组。Auto 入口也可单独关闭，关闭后已有绑定该组的 API Key 后续请求被拒绝，成员选择和价格历史仍保留。

### 12.3 自定义 Auto

用户自定义策略由 ManyRouter 生成带版本的策略快照。首期不要求进入用户请求链路。后续落地时，New API 只读取已经下发的本地快照，运行期间不等待 ManyRouter 计算。

### 12.4 分组内部名称

- 内部名称由稳定业务标识生成，禁止直接使用可修改的展示名称。
- 展示名称、营销文案和内部名称分开保存。
- 删除后重新创建需要新的业务身份，避免旧 API Key 意外指向新产品。
- 内部命名规则进入站点与分组模块设计。

## 13. 供应商统一接入流程

```text
录入供应商
    │
    ├─ 保存共享账号、密钥、模型和采购价格
    ├─ 选择目标站点
    └─ 生成各站点供应商关系
             │
             ▼
       为每个站点生成期望配置
             │
             ├─ 供应商专属分组
             ├─ 一个或多个渠道
             ├─ 分组倍率
             ├─ 入口开放状态
             └─ 初始观察状态
             │
             ▼
       站点执行节点调用 New API
             │
             ▼
       重新读取、绑定实际编号、核对
             │
             ▼
       连通检查与观察期
             │
             ▼
       达标后进入相应 Auto
```

### 13.1 一次录入

供应商地址、共享密钥、模型和采购价格只在 ManyRouter 维护。运营人员选择目标站点后，平台为每个站点自动创建所需资源。

### 13.2 自动绑定

创建完成后，ManyRouter 保存站点、供应商、供应商模型、专属分组和 New API 渠道编号之间的绑定。后续更新依靠绑定定位资源，不使用名称模糊匹配。

### 13.3 部分站点失败

某个站点同步失败时，其他站点的成功结果继续保留。整次供应商投放显示为“部分完成”，失败站点进入重试。运营人员能够看到每个站点的进度和原因。

## 14. 供应商凭证架构

### 14.1 共享原则

同一供应商默认使用一份上游账号和有效密钥。各站点 New API 仍需要保存可发起请求的凭证副本，ManyRouter 记录每个站点已经同步的凭证版本。

共享密钥不会影响站点统计。每个日志来源固定属于一个站点，渠道绑定可以进一步识别供应商和模型。

### 14.2 密钥下发

```text
ManyRouter 加密凭证版本
           │
           ├─► 站点 A 受管渠道
           ├─► 站点 B 受管渠道
           └─► 站点 C 受管渠道
```

- 只有执行对应站点同步的受信进程可以取得所需明文。
- 明文只存在于完成调用所需的短生命周期内。
- 日志、任务载荷和审计不保存明文。
- 每个站点记录凭证版本和最后成功同步时间。

### 14.3 密钥轮换

1. 保存新的加密凭证版本。
2. 使用受控检查确认新凭证可用。
3. 生成涉及所有目标站点的轮换计划。
4. 逐站更新并核对。
5. 全部完成后将新版本设为当前版本。
6. 保留上一版本至安全恢复窗口结束。

某个站点失败时，平台明确显示该站点仍使用的版本。余额耗尽、凭证失效等全局问题会停止所有关联站点的自动流量。

### 14.4 后续独立密钥

数据关系允许为特殊站点绑定独立凭证。该能力以后可以用于供应商限额拆分、企业专线或风险隔离，首期默认流程继续使用共享凭证。

## 15. 请求日志采集架构

### 15.1 日志来源

每个 New API 站点配置独立日志库。New API 继续写入原始日志，ManyRouter 通过只读账号访问一个版本化视图。

```text
New API 请求
    │
    ▼
站点独立日志库
    │ 只读、增量
    ▼
ManyRouter 站点采集器
    │ 标准化与去重
    ▼
ManyRouter 测量事实
```

### 15.2 日志视图

视图只提供评分与用户统计需要的内容：

- 稳定日志游标。
- 请求时间与请求编号。
- 成功或失败类型。
- 模型、渠道和实际分组。
- 首字时间、总耗时和流式状态。
- 上游状态码与经过清洗的错误分类。
- 输入、输出和总用量。
- 重试链中使用过的渠道标识。

用户名、IP、请求正文、响应正文、供应商密钥和其他无关信息不得出现在视图中。

当前 New API 成功日志已经包含毫秒级首字时间，错误日志包含状态码，总耗时字段精度较粗。New API 适配仓库需要补充统一的毫秒级总耗时，并通过版本化日志视图提供。该改动只增加测量事实，不改变请求处理结果。

### 15.3 增量游标

- 每个站点拥有独立采集游标。
- 每批按稳定游标正序读取。
- 数据写入 ManyRouter 成功后才推进游标。
- 相同站点与日志标识重复出现时安全去重。
- 迟到或补写记录通过回看窗口补采。
- HTTP 日志接口作为无法直连日志库时的兼容回退。

### 15.4 请求归并

New API 发生重试时，同一用户请求可能产生多个渠道错误记录和一个最终成功或失败结果。采集模块按请求编号归并为：

- 一次用户请求。
- 多次上游尝试。
- 每次尝试对应的站点、供应商、模型、耗时和错误。
- 最终是否成功及实际完成渠道。

供应商 SLA 使用上游尝试事实计算；用户体验使用最终请求结果计算。两种口径分开保存，避免一次成功重试掩盖前一个供应商的故障。

### 15.5 统计维度

标准化事实至少支持以下聚合：

- 站点。
- 供应商。
- 站点与供应商。
- 供应商与模型。
- 站点、供应商与模型。
- Auto 策略与模型。
- 时间窗口和地区。

上游余额、总限额和凭证状态按供应商全局聚合；用户体验、收入和站点成本按站点分别聚合。

## 16. 主动测评架构

真实流量无法覆盖新供应商、冷门模型、退出 Auto 的线路和长时间无请求时段。主动测评补齐这些空白。

主动测评分为：

- **供应商直连测评**：检查共享账号、余额、模型和供应商自身表现。
- **站点链路测评**：通过指定站点检查完整调用路径和当地网络表现。
- **模型真实性测评**：形成模型级真实性和质量结论。
- **恢复测评**：对已退出或自动停用的对象进行连续复查。

主动数据带有独立来源标记。评分规则可以组合主动数据与真实流量，用户侧统计不能把主动请求计入用户真实请求量。

## 17. 评分与状态架构

### 17.1 两级结论

平台同时维护：

- **供应商全局结论**：凭证、余额、整体限流、跑路风险和大范围模型异常。
- **站点局部结论**：该供应商在某站点的延迟、成功率、网络和同步状态。

全局严重问题会影响所有站点。局部网络或配置问题只影响对应站点。

### 17.2 评分流水线

```text
测量事实
   ↓
窗口统计与样本检查
   ↓
硬性门槛
   ├─ 未通过：排除或停用
   └─ 通过
        ↓
价格、延迟、SLA、质量分项
        ↓
带算法版本的评分快照
        ↓
各站点策略计算成员资格
```

### 17.3 状态层次

需要分开保存以下状态：

- 供应商全局状态。
- 供应商模型状态。
- 站点供应商状态。
- 站点渠道同步状态。
- 供应商在某个 Auto 中的成员状态。

这些状态不能合成一个简单的启用开关。例如供应商可以全局正常、某模型质量异常、在站点 A 延迟过高、在站点 B 正常。

### 17.4 防抖

- 准入线和退出线分开。
- 进入 Auto 前需要满足最小样本量和观察期。
- 普通波动需要连续多个窗口确认。
- 余额耗尽、凭证失效和模型冒充可以立即触发硬性处理。
- 每次成员变化保存使用的统计和规则版本。

## 18. 策略架构

### 18.1 策略定义与站点启用分离

平台统一维护策略定义，例如最低价、低延迟、高 SLA、高质量和均衡。站点启用记录决定：

- 是否在该站点提供此策略。
- 使用哪些候选供应商。
- 是否开放该 Auto 入口。
- 使用哪份评分权重和准入规则。
- 使用什么站点价格。

### 18.2 专属入口与 Auto 入口开放状态

站点策略分别决定供应商专属入口和 Auto 入口是否开放：

- 透明选站型站点可以开放全部合格供应商的专属入口。
- 简单分档型站点可以只开放固定 Auto 入口。
- 混合型站点可以开放部分专属入口和部分 Auto 入口。

用户已确认：关闭入口后，用户不能再选择该组，已有绑定该组的 API Key 后续请求也会被拒绝。关闭保留供应商、渠道、组身份、成员选择、价格与历史；重新开放仍受当前策略和线路状态约束。

专属入口关闭与 Auto 参与独立，该供应商仍可通过其他已开放 Auto 提供服务。Auto 入口关闭也不停止成员在专属组或其他 Auto 中的服务。需要停用供应商全部调用时，使用供应商或投放停用。

适配层沿用 New API 的 `UserUsableGroups` 管理能力。真实合同检查确认关闭后既有 Key 返回 HTTP 403，此结果已成为本次接受的业务行为。底层 `visible` 字段为兼容现有数据继续保留，业务上统一解释为入口开放状态。

### 18.3 策略变化传播

运营人员保存策略后：

1. 形成新的策略版本。
2. 确定受影响站点。
3. 分别重新计算每个站点的期望状态。
4. 为受影响站点生成同步任务。
5. 各站点独立执行和核对。
6. 控制台汇总全部结果。

未受影响站点不生成变更任务。

## 19. 稳定价格架构

### 19.1 价格与路由解耦

```text
评分变化 ──► Auto 成员和分流变化

采购成本显著变化 / 人工调整 ──► 新价格版本
```

线路成员可以频繁小幅调整，用户价格维持当前有效版本。价格模块在预留利润和风险准备范围内吸收供应商成本差异。

### 19.2 价格层次

- 供应商采购价格属于全局供应商数据。
- 供应商专属分组售价属于站点供应商关系。
- 固定 Auto 售价属于站点策略。
- 自定义 Auto 报价属于用户策略快照。

### 19.3 生效流程

价格变化先生成草案和影响范围。通过校验或人工确认后形成有效价格版本，再进入站点期望状态。New API 核对完成后，该站点才标记价格已生效。

部分站点失败时，各站点显示自己的实际生效版本，禁止把全局草案时间当作所有站点的生效时间。

## 20. New API 配置同步架构

### 20.1 M0 同步

M0 使用 New API 现有管理接口逐项完成：

- 创建与更新渠道。
- 维护渠道分组成员关系。
- 启用或停用渠道。
- 更新分组倍率。
- 更新用户可用分组、入口开放状态和 Auto 配置。

由于多项配置无法在一个现有接口中统一提交，M0 采用“保存期望状态、顺序执行、最后核对、失败重试”的方式保证最终一致。

### 20.2 正式同步

New API 适配仓库增加窄权限整批端点：

- 接收期望状态版本和操作编号。
- 在写入前验证完整配置。
- 只允许修改 ManyRouter 受管资源。
- 统一更新渠道、分组、倍率和入口开放配置。
- 刷新 New API 运行缓存。
- 保存 New API 侧审计。
- 返回每项结果和当前实际摘要。

ManyRouter 随后仍需重新读取核对，不能只信任写接口返回值。

### 20.3 站点执行节点

站点执行节点优先通过容器私有网络或本机端口访问 New API，管理端口不需要暴露到公网。它只领取绑定站点的任务，并将结果写回 ManyRouter 平台。

无法部署站点执行节点时，平台任务节点可以通过受保护网络远程调用 New API。两种方式共用同一个兼容适配器。

## 21. 用户请求与用户页面

### 21.1 用户请求

```text
用户客户端
    │ API Key
    ▼
New API
    ├─ 用户与额度检查
    ├─ 根据专属分组或 Auto 选择渠道
    ├─ 转发、重试与计费
    └─ 写入请求日志
           │
           ▼
       上游供应商
```

这个过程不调用 ManyRouter。ManyRouter 只会在之后读取日志并调整下一批请求使用的配置。

### 21.2 用户页面

```text
New API 用户页面
        │ 当前登录状态
        ▼
New API 用户数据代理
        │ 站点签名与用户身份
        ▼
ManyRouter 用户数据服务
        │
        ▼
价格、SLA、延迟、质量、策略与个人统计
```

New API 负责确认当前用户身份。ManyRouter 负责确认站点签名、数据范围和返回内容。供应商内部信息和运营权限不会进入浏览器。

### 21.3 页面降级

ManyRouter 暂时不可访问时，New API 用户请求继续运行。ManyRouter 相关页面显示数据更新时间和暂时不可用状态，禁止影响模型调用页面和 API 请求。

## 22. 多站部署模式

### 22.1 自营站点集群

多个自营站点共用一套 ManyRouter 平台数据库、供应商资料、共享凭证、主动测评和基础评分。站点数据仍以站点身份隔离。

每个新站使用一份经过验证的发布组合：

- 指定版本的 New API。
- 相容版本的 ManyRouter。
- 独立 New API 业务主库。
- 独立 New API 日志库。
- 独立站点身份与管理凭证。
- 可选的站点执行节点。

### 22.2 独立经营者部署

向其他经营者交付时，可以部署独立 ManyRouter 数据库和独立供应商资料。它与自营平台不共享用户、密钥和经营数据。

### 22.3 新站注册流程

1. 使用兼容清单选择 ManyRouter 与 New API 版本。
2. 部署 New API 业务主库和独立日志库。
3. 创建日志只读视图与只读账号。
4. 创建站点管理身份。
5. 在 ManyRouter 登记站点并完成能力检查。
6. 选择该站点启用的供应商和策略。
7. 自动生成并应用初始期望状态。
8. 完成真实调用、日志采集、计费和故障切换验证。

## 23. 一致性模型

ManyRouter 与 New API 之间采用最终一致：配置变化允许有短暂同步时间，完成核对后达到一致。

以下事项采用强一致或事务保护：

- ManyRouter 内部一次业务修改及其新版本。
- 价格草案转为有效价格版本。
- 同一站点期望状态版本的生成。
- 任务领取与幂等记录。
- 共享密钥当前版本切换。

以下事项采用最终一致：

- 供应商投放到多个站点。
- Auto 成员变化同步到 New API。
- 分组价格同步到多个站点。
- New API 实际状态回写 ManyRouter。
- 日志从各站点进入平台统计。

系统优先保证这些安全条件：

- 同步失败时继续使用上一个已确认配置。
- 数据过期时冻结自动扩张和自动恢复。
- 无法确认价格已生效时，禁止对外宣称新价格已经生效。
- 无法确认凭证已同步时，保留旧版本和明确站点状态。
- 人工安全停用不会被后台任务自动覆盖。

## 24. 故障处理

| 故障 | 用户请求影响 | ManyRouter 处理 |
|---|---|---|
| ManyRouter 接口停止 | 已有 New API 请求继续 | 暂停控制台和用户统计更新，恢复后续跑任务 |
| ManyRouter 任务节点停止 | 已有配置继续使用 | River 任务由其他节点领取或恢复后重试 |
| ManyRouter 数据库停止 | 已有 New API 请求继续 | 停止生成和应用新方案，告警并等待恢复 |
| 某站点日志库停止 | 该站请求继续 | 不推进游标，标记数据过期，冻结该站自动调整 |
| 某站点 New API 管理端不可达 | 该站请求按当前配置继续 | 保留待同步版本并重试，不影响其他站点 |
| 供应商单次请求失败 | 由 New API 按现有规则重试 | 后续纳入供应商尝试统计 |
| 供应商持续失败 | 可用线路减少 | 退出对应 Auto，严重时全局停用 |
| 供应商密钥失效 | 多站可能受影响 | 触发全局安全状态，停止关联自动流量并告警 |
| 供应商余额耗尽 | 多站可能受影响 | 全局停用关联渠道，等待充值和恢复检查 |
| 同步部分完成 | 成功站点使用新配置 | 保存逐站结果，仅重试失败站点 |
| New API 版本不兼容 | 当前配置继续使用 | 进入只读模式，禁止自动写入并告警 |
| 统计长时间未更新 | 当前配置继续使用 | 冻结准入、恢复和扩大流量，允许安全退出 |

## 25. 扩展与容量

### 25.1 首期容量

首期面向多个站点、几十家供应商和持续增长的请求日志。使用以下方式控制容量：

- 日志按站点分批增量采集。
- 原始测量与统计结果分开保存。
- 高频页面读取预先生成的统计结果。
- River 按任务类型和站点分配并发。
- 站点同步彼此独立，单站失败不占住其他站点。
- 过期原始数据按保留策略清理。

### 25.2 水平扩展

- 接口节点保持无本地业务状态，可以增加实例。
- 平台任务节点通过 PostgreSQL 协调任务领取。
- 站点执行节点可以按站点数量增加。
- 日志采集可以按站点分区。
- 主动测评可以按供应商和地区分区。
- New API 适配器、供应商适配器和通知适配器可以独立增加实现。

### 25.3 后续拆分条件

继续采用模块化单体，直到出现明确压力。满足下列情况之一时再评估拆分独立服务：

- 日志采集吞吐影响控制台接口。
- 模型检测依赖与主程序运行环境冲突。
- 多地区探测需要独立部署和调度。
- 单个任务类型需要独立扩容或安全权限。
- 独立团队开始长期负责某一模块。

拆分时沿用现有模块能力和任务契约，禁止以复制业务规则的方式拆分。

## 26. 安全边界

### 26.1 网络

- New API 业务主库只允许 New API 自身访问。
- 日志库只读入口只向绑定的 ManyRouter 节点开放。
- New API 管理端口通过本机、容器私网、专用网络或访问控制保护。
- 数据库与管理接口连接使用加密传输。
- 公网只开放用户业务入口和明确允许的控制台入口。

### 26.2 数据库权限

- ManyRouter 自有数据库账号与 New API 日志只读账号分开。
- 每个站点使用独立日志只读账号。
- 日志只读账号只能查询版本化视图。
- 权限测试需要证明账号无法插入、更新、删除或访问排除字段。

### 26.3 密钥与身份

- 供应商密钥在 ManyRouter 中加密保存。
- 每个站点拥有独立 ManyRouter 身份和 New API 管理身份。
- 凭证支持单独撤销、轮换和版本追踪。
- 操作日志只记录凭证版本和动作结果。
- New API 用户身份转发带时间限制和防重放保护。

### 26.4 数据最小化

- ManyRouter 不保存用户请求正文和响应正文。
- 评分只使用状态、耗时、用量、模型、渠道和清洗后的错误事实。
- 用户个人统计使用 New API 用户标识的站点内映射，禁止跨站关联用户身份。

## 27. 可观测性

控制台和监控需要区分：

- **数据新鲜度**：每个站点最后日志时间、最后采集时间和游标位置。
- **决策新鲜度**：最后统计、评分、策略和价格版本时间。
- **同步状态**：每个站点的期望版本、实际版本、最近成功时间和偏差。
- **供应商状态**：全局余额、凭证、模型质量和总体限流。
- **站点表现**：站点级请求、成本、收入、成功率和延迟。
- **任务状态**：等待、执行、失败、重试和永久失败数量。

告警必须指出业务对象、影响站点、当前动作和建议处理方式。单纯的内部错误堆栈不能作为运营告警正文。

## 28. 架构约束

后续模块设计和实现必须遵守：

1. ManyRouter 是受管供应商、站点策略和期望线路的唯一管理入口。
2. 供应商资料和默认上游凭证只维护一次。
3. New API 业务主库禁止直连。
4. New API 日志库仅通过只读、最小字段、版本化视图访问。
5. New API 所有配置写入均通过业务接口完成。
6. 用户请求链路不依赖 ManyRouter 实时在线。
7. 评分版本、策略版本、价格版本和线路版本分别保存。
8. 站点数据从写入第一天起携带站点身份。
9. 供应商全局问题与站点局部问题分别判断。
10. 同步成功必须经过重新读取核对。
11. 人工安全停用优先于自动恢复。
12. 非受管 New API 资源不得被同步任务修改。
13. 新站点使用已经验证的 ManyRouter 与 New API 组合。
14. 模块之间通过稳定业务能力协作，禁止跨模块直接改表。

## 29. 留给模块设计的内容

以下内容需要在对应里程碑启动前，经讨论确认后进入模块设计：

- 站点、供应商、渠道、分组和凭证的具体数据结构。
- New API 日志视图字段和增量游标细节。
- 成功日志、错误日志和重试尝试的归并规则。
- 评分公式、归一化方法、样本门槛和防抖参数。
- 固定 Auto 与自定义 Auto 的策略数据结构。
- 稳定价格公式、调价门槛和生效流程。
- New API M0 接口调用顺序和正式整批端点契约。
- 期望状态、差异计划、幂等操作和回退的数据结构。
- 运营角色、站点身份和签名协议。
- 站点执行节点的注册、任务领取和失联处理。
- 控制台页面结构和具体交互。

## 30. 架构验收标准

进入 roadmap 设计前，架构需要满足：

1. ManyRouter、New API 和上游供应商的职责边界明确。
2. 一个逻辑平台管理多个站点的结构明确。
3. 新建供应商后自动投放多个站点的流程明确。
4. 一个供应商专属分组与多个实际渠道的关系明确。
5. 共享上游密钥和按站点统计可以同时成立。
6. 高频日志只读采集与低频 HTTP 配置写入边界明确。
7. 期望状态、实际状态和最近确认状态的关系明确。
8. 策略修改能够只传播到受影响站点。
9. 价格变化与线路成员变化彼此独立。
10. ManyRouter 故障时 New API 能继续处理已有业务。
11. 多站扩容、任务扩容和未来模块拆分路径明确。
12. 后续模块设计项已经列出，未把关键细节留成无归属问题。
