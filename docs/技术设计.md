## 1. 文档范围

本文确定 ManyRouter 的技术栈、仓库边界、工程目录、数据与接口规范、New API 兼容方式、安全基线、测试门禁和发布规则。

系统整体分层、运行时协作关系、完整数据流和部署拓扑见[架构设计](./架构设计.md)。各业务模块的详细状态、算法、数据结构和接口字段在对应模块设计中确定。

## 2. 已确认技术决策

| 项目 | 决策 |
|---|---|
| 后端语言 | Go |
| Web 框架 | Gin |
| 主数据库 | PostgreSQL |
| 数据访问 | pgx + sqlc |
| 数据迁移 | Goose |
| 后台任务 | River |
| 接口契约 | OpenAPI 优先，生成前后端类型 |
| 控制台 | React 19 + TypeScript 严格模式 |
| 前端构建 | Rsbuild |
| 前端路由与请求 | TanStack Router + TanStack Query |
| 样式与基础组件 | Tailwind CSS 4 + Base UI |
| 多语言 | i18next |
| ManyRouter 前端包管理 | pnpm 10 |
| New API 前端包管理 | 遵循 New API 上游，当前为 Bun |
| 控制台身份 | ManyRouter 独立运营账号 |
| 仓库形态 | ManyRouter 与 New API 适配仓库独立维护 |
| 发布形态 | ManyRouter 与经过验证的 New API 版本组合发布 |
| 首期集成 | ManyRouter 后端调用 New API 现有 HTTP 管理接口 |
| 正式集成 | New API 增加窄权限、可整批操作的 ManyRouter 接入端点 |
| 日志采集 | 只读连接 New API 独立日志库，HTTP 日志接口作为兼容回退 |
| 上游凭证 | 同一供应商默认跨站共享一个账号和密钥 |
| 核心约束 | New API 业务主库禁止直连，所有配置写入通过 HTTP 管理接口 |

## 3. 版本基线

### 3.1 后端

- ManyRouter 的 Go 模块基线使用 Go 1.25.1。
- `go.mod` 必须声明完整基线，并固定构建工具链。
- 开发机可以安装更高版本 Go，但提交前必须通过项目声明工具链的完整门禁。
- 第三方 Go 依赖必须进入 `go.mod` 和 `go.sum`，禁止依赖开发机全局安装的库。
- 生产构建使用固定版本的容器镜像和依赖校验结果。

选择 Go 1.25.1 的原因是当前分析基线中的 New API 已使用该版本，首期组合验证可以减少环境差异。

### 3.2 ManyRouter 控制台

- Node.js 基线使用 24.x，当前验证版本为 24.18.0。
- pnpm 基线使用 10.x，当前验证版本为 10.34.5。
- React 使用 19.x。
- Rsbuild 使用 2.x。
- Tailwind CSS 使用 4.x。
- Base UI 使用 1.x。
- TanStack Query 使用 5.x。
- TanStack Router 使用 1.x。
- 所有直接依赖由锁文件固定到确切版本。

### 3.3 New API 前端

- New API 适配仓库继续使用上游选定的前端工具和锁文件。
- 当前上游使用 React 19、Rsbuild 2、Tailwind CSS 4、Base UI、TanStack Router、TanStack Query 和 i18next。
- 当前上游约定优先使用 Bun；开始修改其前端前，需要按 Bun 官方安装方式补齐本机工具。
- 禁止为了方便在 New API 适配仓库中同时维护多套包管理锁文件。

### 3.4 数据库

- PostgreSQL 17 作为首期生产和持续集成基线。
- ManyRouter 只承诺 PostgreSQL，不增加 SQLite、MySQL 等兼容负担。
- 开发、测试和生产使用相同主版本。
- 容器中的数据库数据使用 Docker named volume，禁止挂载到 Windows 项目目录。

## 4. 仓库与发布边界

### 4.1 ManyRouter 仓库

ManyRouter 仓库包含：

- 供应商、测量、评分、策略、价格和站点业务。
- 后端接口与后台任务。
- 独立运营控制台。
- New API 版本适配客户端。
- 数据迁移、部署模板和项目文档。
- 自动化测试与兼容验证工具。

### 4.2 New API 适配仓库

New API 适配仓库基于官方仓库维护，并持续保留上游来源。改动范围控制在：

- ManyRouter 用户侧页面与导航入口。
- 将当前登录用户的只读数据请求转发给 ManyRouter。
- 面向 ManyRouter 的版本与能力检查。
- 窄权限的整批分组、价格和状态操作。
- 后续确有需要时增加的本地策略读取或统计采集点。

New API 的用户、计费、协议转换和转发能力继续沿用上游实现。所有修改必须遵守上游许可证、署名和源码提供要求。

### 4.3 当前源码目录

`C:\code\ManyRouter\new-api` 当前作为上游源码分析和首个适配基线，官方源码基线提交为 `0ed497f0`。该目录拥有独立 Git 历史，不进入 ManyRouter 主仓库历史。

正式开发 New API 适配仓库前，需要明确仓库地址、上游远端和发布命名。ManyRouter 发布记录只引用经过验证的提交、标签或镜像摘要。

### 4.4 组合发布

- ManyRouter 与 New API 分别发布版本和容器镜像。
- 每次站点发布使用一份组合清单固定两个版本。
- 组合清单同时记录 PostgreSQL 版本、数据库迁移版本和 New API 兼容结论。
- 发布包禁止使用浮动的 `latest` 作为生产依据。
- 建立新站点时，只能选择已经通过完整验证的组合。

## 5. 后端工程方案

### 5.1 程序形态

ManyRouter 首期使用一个 Go 模块和一个可执行程序。可执行程序提供以下运行模式：

- `serve`：提供控制台和后端接口。
- `worker`：执行日志采集、主动测评、评分、价格和线路调整任务。
- `migrate`：显式执行数据库迁移。
- `all`：在单站、小规模环境中同时运行接口与后台任务。

首期部署默认使用 `all`。规模增加后，可以直接将接口和后台任务拆成不同进程，继续使用相同代码与任务数据。

### 5.2 业务模块

后端按业务职责划分模块：

- 站点管理。
- 供应商与模型管理。
- 真实流量采集。
- 主动测评。
- 模型真实性与质量检测。
- 评分。
- Auto 策略。
- 稳定价格。
- 线路方案与执行核对。
- New API 适配。
- 通知。
- 审计。
- 运营账号与权限。

每个模块保存自己的业务规则。一个模块不得直接修改另一个模块的数据表；跨模块操作通过应用用例完成。

### 5.3 外部适配边界

容易变化的外部能力统一放在适配层：

| 适配类别 | 统一能力 |
|---|---|
| 网关适配 | 读取版本、读取渠道、读取日志、应用线路方案、更新价格、停用与恢复 |
| 供应商适配 | 获取模型、获取价格、获取余额、执行连通检查 |
| 检测适配 | 执行模型真实性或能力测试并返回统一结果 |
| 通知适配 | 发送告警并返回可追踪结果 |
| 存储适配 | 保存和读取统一业务对象 |

首期采用编译时注册。动态安装第三方插件、在线加载未知代码和跨平台 Go 动态插件暂不建设。

### 5.4 错误处理

- 业务错误、外部依赖错误、数据错误和系统错误使用明确分类。
- 错误必须包含可稳定识别的错误码、便于运营理解的消息和请求编号。
- 外部返回内容进入日志前必须去除密钥、令牌、请求正文和其他敏感数据。
- 后台任务失败必须区分可重试、需要人工处理和永久失败。
- 禁止忽略 Go 返回的错误。
- 发生部分成功时，必须明确记录已完成和未完成的对象。

## 6. 数据访问与数值规范

### 6.1 数据访问

- ManyRouter 自有数据通过 sqlc 生成的类型安全查询访问 PostgreSQL。
- ManyRouter 自有数据库运行时使用 pgx 连接池。
- SQL 按业务模块组织，禁止在接口处理代码中拼接查询。
- 动态筛选使用参数化查询，禁止拼接用户输入。
- 跨多个业务对象的状态变化使用数据库事务。
- 查询需要明确分页、排序和最大返回量。

### 6.2 New API 日志库只读访问

- 每个受管 New API 站点使用独立日志库，禁止将高频统计查询施加到 New API 业务主库。
- ManyRouter 为每个站点使用独立只读数据库账号。
- 只读账号只允许查询版本化日志视图，不授予基础表、其他视图、序列和写入权限。
- 日志视图只暴露统计所需字段，排除用户名、IP、请求正文、访问密钥和其他无关敏感信息。
- 使用站点身份与日志游标共同记录采集位置，按稳定顺序增量读取，禁止依赖总数统计和偏移翻页。
- 读取批次支持重复执行，并在 ManyRouter 自有数据库中去重。
- 日志视图变化属于 New API 兼容契约，需要版本检查和合同测试。
- New API 日志库暂时不可用时，停止推进该站点游标并进入重试，禁止将缺失数据视为零请求或零失败。
- ManyRouter 运行账号不得拥有 New API 日志库的写权限。

### 6.3 数据迁移

- Goose 迁移文件只追加，已经进入发布版本的迁移禁止修改内容。
- 迁移必须同时提供向前步骤和可行的回退步骤。
- 破坏性变化采用“先兼容、再迁移数据、最后删除旧字段”的分阶段方式。
- 应用启动不自动执行未知迁移；部署流程先执行迁移，再启动新版本。
- 每次发布验证空数据库初始化和上一正式版本升级。

### 6.4 数据分类

ManyRouter 数据分为：

- 全局供应商资料与模型目录。
- 原始测量记录。
- 评分与价格历史版本。
- 全局可共享的供应商基础结论。
- 站点独立的产品、价格、策略和线路方案。
- 站点、供应商、渠道、分组之间的对应关系与同步状态。
- 站点独立的用户关联统计。
- 后台任务、通知和操作审计。

所有站点范围内的数据从首版开始携带站点身份。共享数据不得包含其他站点的用户身份、余额、订单或请求正文。

### 6.5 历史数据

- 原始测量、价格版本、评分快照、线路方案和操作审计采用追加方式保存。
- 当前状态与历史版本分开查询。
- 聚合结果需要记录统计窗口、样本量、生成时间和算法版本。
- 原始数据保留周期可配置，删除前先生成长期聚合结果。
- 同一来源重复上报的数据通过稳定业务标识去重。

### 6.6 数值与时间

- 金额和成本禁止使用二进制浮点数直接计算。
- 数据库金额使用固定精度十进制；Go 内部使用十进制库或明确的最小货币单位。
- 写入 New API 倍率前统一执行精度、范围和非负校验。
- 延迟统一使用整数毫秒。
- 比率、成功率和权重需要定义固定精度和上下限。
- 所有持久化时间使用 UTC。
- 对外接口使用带时区的 ISO 8601 时间。
- 页面根据用户选择的时区展示。

## 7. 后台任务

### 7.1 任务底座

- 使用 River 在 PostgreSQL 中保存后台任务。
- 禁止依赖进程内定时器作为唯一任务来源。
- 定时任务、立即任务和失败重试使用同一任务机制。
- 每种任务拥有明确类型、载荷版本、超时、重试次数和并发限制。
- 任务处理必须支持重复执行。

### 7.2 首期任务类型

- 拉取 New API 增量日志。
- 聚合真实流量。
- 执行供应商和模型测评。
- 查询余额与价格。
- 生成评分快照。
- 生成 Auto 成员与线路方案。
- 生成稳定报价。
- 将方案应用到 New API。
- 核对应用结果。
- 生成和发送通知。
- 清理超过保留期的原始数据。

### 7.3 多进程协调

- 相同站点、供应商或策略的互斥任务不得并发修改同一状态。
- 任务锁、重试状态和执行结果保存在 PostgreSQL。
- 多个执行进程可以竞争不同任务。
- 执行进程异常退出后，任务能够重新领取。
- 对 New API 的写操作必须携带稳定操作编号，防止重试造成重复变化。

## 8. 接口契约

### 8.1 契约优先

- 使用 OpenAPI 3.0.3 文件定义 HTTP 接口。
- Go 服务端类型和 TypeScript 客户端类型从契约生成。
- 生成文件禁止手工修改。
- 契约、生成结果和实现必须在同一次提交中更新。
- 持续集成检查生成结果没有漂移。

### 8.2 接口分区

| 分区 | 用途 | 身份来源 |
|---|---|---|
| 公开统计 | 价格、SLA、延迟、质量和可用数量 | 按站点限制，无用户身份 |
| 用户统计 | 用户请求统计、自定义策略和报价 | New API 已登录用户 |
| 站点接入 | New API 后端读取 ManyRouter 数据 | 站点专用凭证 |
| 运营管理 | 供应商、策略、价格、站点和人工操作 | ManyRouter 运营账号 |
| 内部任务 | 任务执行与结果回报 | 内部进程身份 |

### 8.3 通用规则

- ManyRouter HTTP 接口统一使用 `/api/v1` 前缀。
- JSON 字段采用 `snake_case`。
- 错误响应至少包含稳定错误码、用户可理解消息和请求编号。
- 列表接口使用游标分页，禁止以无限制全量列表作为常规接口。
- 写接口支持幂等键。
- 更新当前状态时支持版本检查，防止旧页面覆盖新结果。
- 所有接口明确超时、最大请求体和最大分页大小。
- 接口删除或改变语义前，先提供兼容期和迁移说明。

## 9. 身份与权限

### 9.1 ManyRouter 运营账号

- ManyRouter 维护独立运营账号，不复用任何单个 New API 站点的管理员账号。
- 首次部署通过一次性初始化流程创建所有者账号。
- 初始化完成后，一次性凭证立即失效。
- 密码使用 Argon2id 保存。
- 登录使用服务端会话和安全 Cookie。
- 所有改变状态的网页请求启用 CSRF 防护。
- Cookie 在生产环境必须启用 `HttpOnly`、`Secure` 和合适的 `SameSite` 策略。

权限从首版按以下角色设计：

- 所有者：账号、安全和全部站点权限。
- 管理员：供应商、策略、价格、站点和人工处置。
- 观察员：只读统计、告警和审计。

首期可以只开放所有者账号，但数据结构和权限检查必须支持后续增加管理员与观察员。

### 9.2 站点身份

- 每个 New API 站点拥有独立的 ManyRouter 接入身份。
- 一个站点凭证泄露时，可以单独撤销，其他站点不受影响。
- New API 后端向 ManyRouter 转发用户请求时，需要携带站点、用户、角色、时间和请求摘要的签名。
- 签名使用每站独立密钥，并校验时间窗口与防重放信息。
- 浏览器不能获得站点签名密钥。

### 9.3 ManyRouter 操作 New API

- M0 使用 New API 支持的访问令牌调用现有管理接口。
- 每个站点使用独立 New API 服务账号和凭证。
- 凭证只保存在 ManyRouter 后端。
- 正式版使用窄权限接入端点，停止长期使用 New API 最高权限凭证。
- New API 端记录 ManyRouter 发起的每次写操作及其业务原因。

### 9.4 供应商上游凭证

- 同一供应商的上游账号和密钥在 ManyRouter 中维护一份有效来源。
- 供应商凭证默认同步到所有启用该供应商的自营站点。
- 每个站点记录已同步的凭证版本，禁止依靠密钥差异完成站点统计。
- 密钥轮换先验证新凭证，再逐站同步；全部目标站点确认成功前保留上一版本用于恢复。
- 上游余额、总限额和凭证失效按供应商全局状态处理。
- 某个站点的流量异常、延迟异常或配置失败可以只影响该站点的渠道状态。
- 数据结构保留按站点绑定不同凭证的能力，首期不作为默认流程。

## 10. New API 集成

### 10.1 集成原则

- ManyRouter 通过只读日志视图采集高频请求事实，通过 HTTP 接口读取和修改 New API 运行配置。
- 禁止连接 New API 业务主库、直接修改任何 New API 表或依赖其缓存内部结构。
- New API 日志数据库只允许读取版本化视图，禁止写入。
- ManyRouter 核心模块不得出现 New API 的渠道字段、权限常量和页面数据结构。
- New API 差异只存在于网关适配层和 New API 适配仓库。
- 用户请求过程中不向 ManyRouter 发起同步评分请求。

### 10.2 M0 使用现有接口

M0 通过现有 New API 能力完成业务验证：

- 读取渠道和分组。
- 更新渠道所属分组、状态、优先级和权重。
- 通过独立日志库只读视图增量采集请求日志。
- 在日志库不可直连时，通过 HTTP 日志接口完成兼容采集。
- 修改分组倍率和 Auto 配置。
- 读取 New API 状态与版本信息。

适配层必须处理游标、分页、业务错误、鉴权失败、超时、重复写入和版本差异。禁止由评分模块直接访问日志库或发起上述请求。

### 10.3 正式接入端点

正式版本在 New API 适配仓库中增加一个独立接入前缀。它只提供：

- 版本和能力查询。
- ManyRouter 管理身份验证。
- 当前受管线路状态查询。
- 整批应用分组成员、状态与价格变化。
- 根据操作编号查询结果。
- 写入 New API 侧审计记录。

整批操作需要先完整校验，再统一应用。发生失败时返回清晰的失败对象和原因，ManyRouter 随后执行结果核对与修复。

### 10.4 用户侧页面接入

- New API 用户页面只调用同源的 New API 后端。
- New API 后端验证当前用户后，将允许的请求转发给 ManyRouter。
- ManyRouter 根据站点与用户身份返回公开或用户范围内的数据。
- 供应商凭证、真实采购成本和内部评分细节不得经过用户侧接口。
- ManyRouter 暂时不可用时，页面显示数据暂时无法更新；已有模型请求继续由 New API 处理。

### 10.5 转发链扩展条件

首期不在 New API 用户请求转发链增加 ManyRouter 调用。仅在以下情况经过模块设计和回归验证后增加本地扩展点：

- 现有日志缺少不可替代的统计事实。
- 用户级自定义 Auto 需要读取预先下发的本地策略。

扩展点只能读取 New API 本机缓存或异步记录事实。同步远程调用、临时评分和长时间等待禁止进入转发链。

## 11. New API 版本兼容

### 11.1 兼容声明

每个 ManyRouter 版本发布以下信息：

- 最低支持的 New API 版本或提交。
- 已验证的最高 New API 版本或提交。
- 推荐组合版本。
- 已验证能力列表。
- 已知限制和升级说明。

当前 `0ed497f0` 只作为首个源码分析基线。完成真实集成与合同测试后，才能将其声明为最低支持版本。

### 11.2 能力检查

适配器根据能力判断可用操作，包括：

- 渠道读取与修改。
- 分组成员修改。
- 状态启停。
- 版本化日志视图或 HTTP 日志增量读取。
- 分组价格修改。
- 整批方案应用。
- 用户侧数据转发。

判断依据以实际能力响应和合同测试为准，禁止只比较字符串版本号。

### 11.3 适配器版本

- 网关适配器对 ManyRouter 核心提供稳定统一能力。
- 相同接口行为的 New API 版本共享一个适配器。
- 出现破坏性差异时新增适配器实现。
- 旧适配器在其支持范围内继续接受回归测试。
- 删除旧版本支持需要先更新兼容声明和迁移说明。

### 11.4 升级策略

- 生产站点只执行人工发起的版本升级。
- 上游新版本先进入兼容测试，再更新推荐组合。
- 升级前保存当前组合和配置备份。
- 升级失败时能够恢复到上一个已验证组合。
- New API 上游改动定期合入适配仓库，禁止长期堆积一个大型升级。

## 12. 前端工程方案

### 12.1 ManyRouter 控制台

- TypeScript 必须开启 `strict`。
- 同时开启未检查索引访问、精确可选属性、未使用代码和 switch 穿透检查。
- 使用 TanStack Router 管理路由。
- 使用 TanStack Query 管理服务端状态。
- 组件本地状态只保存页面交互，不复制服务端事实。
- 接口类型从 OpenAPI 契约生成。
- 用户可见文本统一进入 i18next。
- 金额、日期、百分比和延迟使用统一格式化工具。

### 12.2 设计系统

- 开发业务页面前先建立主题 Token 和基础组件。
- 统一定义色彩、字体、字号、间距、圆角、边框、阴影、控件尺寸和响应式断点。
- 页面禁止散落重复的视觉常量。
- 控制台优先保证高密度信息浏览、筛选、比较和重复操作效率。
- 所有页面覆盖加载、空数据、错误、无权限和长文本状态。
- 纯外观不写单元测试，通过浏览器和截图验证。

### 12.3 功能组织

控制台按业务功能划分目录：

- 站点。
- 供应商。
- 模型测评。
- 评分。
- Auto 策略。
- 价格。
- 线路变化。
- 告警。
- 审计。
- 运营账号。

每个功能目录包含页面、组件、请求、数据类型和有业务价值的纯函数测试。跨功能通用组件进入基础组件层。

### 12.4 New API 用户页面

- 使用 New API 现有设计系统、组件和国际化方式。
- ManyRouter 页面集中在独立功能目录。
- 对上游通用组件的修改保持最小。
- 新增文案覆盖 New API 当前支持语言；首期至少保证中文与英文完整。
- New API 用户页面只展示当前站点允许公开的数据。

## 13. 配置与密钥

### 13.1 配置分类

启动配置通过环境变量提供：

- 数据库连接。
- 服务监听地址。
- 主加密密钥。
- 初始设置凭证。
- 日志级别。

运营配置通过控制台保存：

- 站点信息。
- New API 连接与兼容配置。
- 供应商和模型。
- 评分、准入和退出规则。
- Auto 策略。
- 价格与利润。
- 任务频率。
- 通知渠道。

### 13.2 密钥保护

- 供应商密钥、New API 管理凭证和站点签名密钥加密保存。
- 使用 AES-256-GCM 等带完整性校验的加密方式。
- 主加密密钥只通过运行环境注入，不写入数据库、源码或日志。
- 密文记录携带密钥版本，支持后续轮换。
- 接口默认返回脱敏值，修改密钥使用单独动作。
- 操作审计只记录“已新增”“已替换”“已撤销”等结果。

### 13.3 配置校验

- 配置在保存前执行格式、范围和相互依赖检查。
- 影响价格、停用或大批量分组的修改需要明确确认。
- 保存后生成新配置版本。
- 后台任务使用启动时确定的配置快照，执行中不混用两个版本。

## 14. 日志、指标与审计

### 14.1 应用日志

- 后端使用 Go 标准结构化日志能力输出 JSON。
- 日志至少包含时间、级别、服务模式、请求编号、站点、任务、业务动作和结果。
- 禁止记录完整访问密钥、登录凭证和用户请求正文。
- 外部错误正文只保留经过清洗的摘要。

### 14.2 运行指标

至少提供：

- HTTP 请求量、失败量和耗时。
- 后台任务等待量、执行量、失败量和耗时。
- New API 拉取延迟与最后成功时间。
- 评分和线路方案最后更新时间。
- 各站点应用方案成功率。
- 数据库连接池和任务执行器状态。

指标名称和标签保持稳定，禁止把用户编号、请求编号等高数量值作为指标标签。

### 14.3 审计

- 人工和自动写操作进入统一审计记录。
- 审计包含操作者、站点、对象、业务原因、旧值摘要、新值摘要、操作编号、时间和结果。
- 自动重试关联同一个操作编号。
- 审计记录只追加，普通业务操作不能修改或删除。

建议目录如下：

```text
ManyRouter/
├─ cmd/
│  └─ manyrouter/              程序入口与运行模式
├─ internal/
│  ├─ domain/
│  │  ├─ site/                 站点业务对象与规则
│  │  ├─ supplier/             供应商与模型
│  │  ├─ measurement/          测量事实
│  │  ├─ scoring/              评分
│  │  ├─ strategy/             Auto 策略
│  │  ├─ pricing/              稳定价格
│  │  └─ routing/              线路方案
│  ├─ application/
│  │  ├─ onboarding/           供应商接入用例
│  │  ├─ collection/           数据采集用例
│  │  ├─ evaluation/           评估与准入用例
│  │  ├─ reconciliation/       方案应用与核对用例
│  │  └─ quoting/              报价用例
│  ├─ adapters/
│  │  ├─ gateway/              New API 版本适配
│  │  ├─ supplier/             供应商类型适配
│  │  ├─ detector/             模型检测适配
│  │  ├─ storage/              PostgreSQL 实现
│  │  └─ notification/         通知实现

│     └─ observability/        日志与指标
├─ api/
│  └─ openapi.yaml             接口契约
├─ db/

├─ deploy/                     组合部署模板
```

目录规则：

- `domain` 不导入 Gin、pgx、River 或 New API 客户端。
- `application` 负责组合业务步骤，不包含 HTTP 和 SQL 细节。
- `adapters` 实现外部系统和存储差异。
- `transport` 只处理协议、身份、校验和响应转换。
- `jobs` 只负责领取任务并调用应用用例。
- 单个文件保持单一职责，复杂模块继续拆分子目录。
- 生成代码集中存放并明确标记，禁止与手写业务代码混杂。

## 16. 可扩展性规则

### 16.1 新供应商类型

新增供应商协议时，只增加供应商适配实现与合同测试。供应商、评分、价格和策略模块继续使用统一结果。

### 16.2 新网关或 New API 新版本

新增网关或破坏性 New API 版本时，只增加网关适配实现、能力声明和兼容测试。核心业务不得依赖版本分支。

### 16.3 新评分维度

- 评分明细按维度保存。
- 新维度通过注册进入评分计算。
- 硬性门槛与可加权维度分开。
- 旧评分快照保留其算法版本，禁止用新算法覆盖历史结果。

### 16.4 新策略与价格规则

- 新策略读取统一评分快照并生成统一线路方案。
- 新价格规则读取统一采购成本与策略结果。
- 价格结果形成版本后再对外使用。
- 规则变化需要新增测试样例和变更记录。

### 16.5 新站点功能

- 站点差异通过配置和功能开关表达。
- 站点专属展示进入前端功能模块。
- 禁止复制整套后端并修改站点专属逻辑。
- 会影响数据隔离和计费的功能开关必须由后端执行权限检查。

### 16.6 新通知和报表

通知和报表消费已经保存的业务事件或历史事实。它们不得阻塞评分、价格和线路方案的主流程。

## 17. 测试策略

### 17.1 后端单元测试

必须覆盖：

- 四维评分和硬性门槛。
- 最小样本量与时间窗口。
- Auto 准入、退出和恢复。
- 严重故障全局停用。
- 稳定价格、利润和风险准备。
- 金额精度和倍率边界。
- 幂等操作与版本冲突。
- 多站数据隔离。

测试使用确定输入和精确预期，禁止通过随机循环、休眠或日志输出来判断业务正确性。

### 17.2 PostgreSQL 集成测试

必须覆盖：

- 空数据库迁移。
- 上一正式版本升级。
- 事务与并发更新。
- River 任务领取、重试和恢复。
- 历史事实去重。
- 站点隔离查询。
- New API 日志游标续传、迟到记录和重复批次。
- 日志只读账号无法修改基础表或日志视图。

### 17.3 New API 合同测试

每个声明支持的 New API 版本都需要运行：

- 身份验证。
- 渠道和分组读取。
- 分组成员修改。
- 渠道启停。
- 日志增量读取。
- 分组倍率更新。
- 整批方案应用与结果查询。
- 用户侧数据转发。
- ManyRouter 不可用时的降级表现。

使用日志库直连的组合还必须验证日志视图字段、排序稳定性、权限边界和错误日志与成功日志的归并规则。

测试必须使用真实 New API 进程和数据库，单纯模拟响应不能作为兼容结论。

### 17.4 前端测试

- 价格计算、表单转换、权限判断和状态计算等纯逻辑使用 Vitest。
- 主题、颜色、间距、布局和组件外观不写单元测试。
- 关键页面通过真实浏览器检查加载、空数据、错误、长文本和响应式布局。
- New API 用户页面需要在每个支持版本上完成构建和关键流程验证。

## 18. 项目门禁

### 18.1 日常门禁

根目录提供统一的 `pnpm gate`，至少执行：

- Go 格式检查。
- Go 静态分析。
- Go 单元测试。
- OpenAPI 与生成代码漂移检查。
- TypeScript 严格类型检查。
- 前端代码检查。
- 前端逻辑测试。
- 后端和前端生产构建。

### 18.2 专项门禁

- 数据库或任务变化运行 PostgreSQL 集成门禁。
- New API 适配变化运行完整兼容矩阵。
- 前端界面变化运行真实浏览器视觉检查。
- 发布前运行全部日常和专项门禁。

### 18.3 Go 静态要求

- 使用 `gofmt` 与 `goimports`。
- 使用 `go vet`、Staticcheck 和 golangci-lint。
- 开启未处理错误、无效 SQL 资源、HTTP 响应体泄漏和不完整 switch 检查。
- 生产代码禁止使用 `panic` 表达普通业务失败。
- 全局可变状态需要明确并发保护或消除。

## 19. 本地开发与容器

- 源码、Git、Go、Node.js、pnpm、格式化、静态检查、测试和构建使用 Windows 工具链。
- PostgreSQL、New API 兼容测试和组合环境使用 WSL 2 中的 Docker。
- Windows、WSL 和容器分别维护各自缓存及依赖目录。
- 禁止跨环境共享 `node_modules`、Go 构建缓存、数据库目录和运行时索引。
- Docker Compose 命令从 WSL 明确指定 `Ubuntu-24.04` 和 `/mnt/c/code/ManyRouter` 工作目录。
- 数据库使用 named volume。
- 仓库使用 `.gitattributes` 固定文本换行，Windows Git 使用 `core.autocrlf=false`。
- 开发和测试命令不得默认启动长期驻留的开发服务器。

## 20. 发布与回退

- ManyRouter 使用语义化版本。
- 数据库迁移版本、OpenAPI 版本和兼容清单随发布保存。
- 容器镜像使用不可变标签和摘要。
- 发布前生成变更说明、升级步骤和回退步骤。
- New API 适配仓库的构建产物保留上游要求的许可证与署名。
- 站点升级先验证迁移和兼容能力，再切换服务。
- 自动线路方案、价格和站点配置在升级前备份。
- 回退后继续识别升级期间已经生成的任务和操作记录。

## 21. 暂缓的技术能力

以下能力等待明确业务需求后再设计：

- 第三方动态插件市场。
- 在线执行未知供应商代码。
- SQLite、MySQL 等多数据库兼容。
- 多个站点共用一套用户账号和余额。
- 每个请求同步调用 ManyRouter 进行评分。
- 将 ManyRouter 业务代码合入 New API 转发核心。
- 为每家站点维护独立后端代码分支。

## 22. 技术设计验收标准

进入架构设计前，本技术设计需要满足：

1. 技术栈、版本基线和包管理方式明确。
2. ManyRouter 与 New API 的仓库和发布边界明确。
3. 日志库只读采集、M0 HTTP 控制与正式窄权限集成路径明确。
4. 独立运营账号、站点身份和密钥保护基线明确。
5. PostgreSQL、后台任务、金额和时间规范明确。
6. OpenAPI、版本兼容和合同测试规则明确。
7. 前端技术栈、严格模式和设计系统规则明确。
8. 目录结构、扩展边界和禁止依赖关系明确。
9. 日常门禁、专项门禁和发布回退规则明确。
10. 文档内容与[需求设计](./需求设计.md)一致，未提前规定模块内部实现。
