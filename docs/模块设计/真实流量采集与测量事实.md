# 真实流量采集与测量事实模块设计

> 模块定位：从各 New API 站点增量读取真实请求日志，形成可追溯、可去重、可按供应商归因的测量事实
> 对应代码：规划为 `internal/domain/measurement`、`internal/application/collection`、`internal/adapters/gateway/newapi/logs`、`internal/adapters/storage/postgres/measurement_*.go`、`internal/jobs/collection_*.go`、`db/query/measurement*.sql`（尚未实现）
> 所属里程碑：[M2 - 建立可信观测与影子评分](../roadmap.md#m2)
> 当前状态：进行中
> 最近更新时间：2026-09-05
> 架构依据：[内部分层](../架构设计.md#7-manyrouter-内部分层)、[测量与采集](../架构设计.md#85-测量与采集)、[请求日志采集](../架构设计.md#15-请求日志采集架构)、[可观测性](../架构设计.md#27-可观测性)

## 1. 职责与边界

本模块负责：

- 为每个站点维护独立采集位置，按稳定顺序增量读取版本化日志视图。
- 将 New API 的成功日志、错误日志和重试信息统一成一次用户请求及其多次上游尝试。
- 在写入时固化站点、供应商、站点供应商关系、模型和外部渠道的对应关系。
- 明确记录首字时间、总耗时、用量、错误归属和流式响应是否正常结束。
- 对重复批次、迟到记录、进程重启和部分失败提供可恢复处理。
- 只保存统计所需字段，拦截用户身份、IP、请求正文、响应正文和凭证。

本模块不计算窗口统计、评分或成员建议，这些能力属于[窗口统计与影子评分](./窗口统计与影子评分.md)。它也不主动发起模型请求，不修改 New API 数据，不改变真实线路；低频探测由[主动测评与模型真实性](./主动测评与模型真实性.md)负责。

## 2. 结构与数据流

### 2.1 计划目录

| 位置 | 职责 |
|---|---|
| `internal/domain/measurement/` | 请求事实、上游尝试、来源、错误分类和完整性规则 |
| `internal/application/collection/` | 单站批次采集、归并、映射、落库和游标推进 |
| `internal/adapters/gateway/newapi/logs/` | New API 版本识别、只读视图和 HTTP 回退适配 |
| `internal/adapters/storage/postgres/measurement_*.go` | 测量事实、采集位置和待归因记录的 PostgreSQL 实现 |
| `internal/jobs/collection_*.go` | 按站点领取采集任务、重试和调度 |
| `db/query/measurement*.sql` | 类型安全查询及批量写入 |
| `compatibility/` | 各受支持 New API 版本的日志合同样本与验证 |

目录在实现时可以继续按读取、归并和存储拆分，业务规则留在领域层和应用层，接口处理与任务入口只负责校验和调用。

### 2.2 数据流

```text
站点采集任务
    -> 读取站点版本、日志能力和当前采集位置
    -> 从版本化只读视图读取一个有序批次
    -> 校验字段、时间和来源
    -> 按请求编号归并最终请求与上游尝试
    -> 用外部渠道映射站点供应商和全局供应商
    -> 同一事务追加测量事实并推进采集位置
    -> 发布“新测量事实可统计”事件
```

任何一步失败都保留原采集位置。下次任务可以重读同一批，唯一约束保证重复数据不会产生第二份事实。

### 2.3 数据来源

主路径为每个站点的独立日志库和版本化只读视图。HTTP 日志接口只在数据库无法直连时作为兼容路径，并遵守相同字段、游标和去重约定。

M2 使用以下来源标记：

| 来源 | 含义 | 是否计入真实用户请求量 |
|---|---|---|
| `real_traffic` | New API 实际用户请求 | 是 |
| `direct_probe` | ManyRouter 直连供应商的主动测评 | 否 |
| `site_probe` | 经指定站点完成的主动测评 | 否 |

本模块只采集 `real_traffic`。三类数据进入统一测量事实后仍保留来源，统计时不得混成同一请求量。

## 3. 核心数据

### 3.1 站点采集位置

每个“站点 + 日志合同版本 + 日志类别”保存一条采集位置，至少包含：

- 已成功提交的来源时间与来源编号组合。
- 最后一次读取、成功提交和源端最新记录时间。
- 最近错误、连续失败次数和下次重试时间。
- 当前是否存在数据缺口、回看起点和合同版本。

优先使用日志视图提供的单调递增编号。只提供时间时，使用“时间 + 稳定编号”作为组合位置，不能依赖偏移分页或总行数。

### 3.2 用户请求事实

一次用户请求只保存一条最终事实，至少包括：

| 内容 | 说明 |
|---|---|
| 来源身份 | 站点、合同版本、来源日志编号和请求编号 |
| 请求范围 | 实际分组、请求模型、开始时间和请求类型 |
| 最终结果 | 成功、失败、用户取消、拒绝或结果不完整 |
| 最终渠道 | 实际完成请求的外部渠道及对应供应商；没有完成渠道时为空 |
| 用户体验 | 首字时间、总耗时、流式开始和正常结束标记 |
| 用量 | 输入、输出、缓存及总用量；缺失与数值零分开表示 |
| 完整性 | 来源字段是否齐全、是否可用于用户体验统计及缺失原因 |

首字时间从站点接受请求开始，到第一个实际向用户输出的内容为止。只包含用量或控制信息的流式块不算首字。总耗时使用毫秒，并覆盖到最终成功、明确失败或连接终止。流式成功必须有明确正常结束证据，不能只凭 HTTP 200 推断。

### 3.3 上游尝试事实

一次用户请求可以关联多条上游尝试。每条尝试至少保存：

- 尝试序号、站点、外部渠道、站点供应商、全局供应商和实际模型。
- 尝试开始时间、首字时间、总耗时和是否产生用户可见内容。
- 上游状态码、稳定错误码、错误归属和可重试结论。
- 是否因限流、余额、鉴权、超时、传输中断、模型不支持或站点内部错误结束。
- 是否为最终完成尝试，以及后续是否切换到其他供应商。

供应商 SLA 使用尝试事实；用户体验使用请求事实。最终成功不能覆盖之前供应商的失败，重复尝试也不能被算作多个用户请求。

### 3.4 供应商归因

采集时根据“站点 + 外部渠道编号”查找 M1 已保存的站点供应商关系，并将当时的映射固化到事实中。后续渠道改名、重建或供应商退出不会改写历史归因。

找不到映射时保留原始渠道编号并标记“待归因”。待归因记录可以在映射补齐后重放归因，但在解决前不进入供应商评分。多个供应商共用同一真实上游时仍按 ManyRouter 的独立供应商记录统计，同时在内部保留真实上游相同这一验收边界。

## 4. 采集与一致性规则

### 4.1 提交顺序

一个批次在同一事务中完成：

1. 锁定该站点采集位置。
2. 写入请求事实、尝试事实和待归因问题。
3. 确认批次最后一条来源记录已经写入或由唯一约束确认存在。
4. 推进采集位置并记录批次结果。

进程在任一步退出后都可以重放。游标领先于事实、跨站共用游标和失败后跳过来源记录都视为数据完整性错误。

### 4.2 迟到与补写

正常任务每次额外回看最近一段已提交范围。来源记录的唯一身份负责去重，更新时间负责识别补写。发现来源日志被补充了上游尝试或终止状态时，追加更正事实并保留前一版本，统计模块只读取最新有效版本。

回看时长作为站点采集配置保存。超过回看范围的历史修复通过显式回填任务执行，不能静默移动正常游标。

### 4.3 错误分类

优先采用上游状态码、New API 稳定错误码、错误阶段和失败归属。文本匹配只作为兼容兜底，并记录分类规则版本。用户参数错误、用户鉴权错误和内容限制等用户原因与供应商故障分别保存。

错误正文进入适配器后立即清洗。数据库只保存稳定分类和短摘要，密钥、令牌、用户正文及完整上游响应不得进入 ManyRouter。

### 4.4 数据缺口

日志库不可达、合同不兼容、字段缺失、来源记录丢失或采集落后都需要形成显式缺口。存在缺口的时间段不能显示成零请求、零失败或满分可用，并由评分模块降低可信度或停止生成建议。

## 5. 关键决策

1. 将最终用户请求和每次上游尝试分开保存，分别回答用户体验和供应商表现。
2. 采集时固化供应商映射，禁止在统计时依据当前渠道配置反推历史。
3. 成功由明确结果字段判定，不能用“产生费用”“用量大于零”代替。
4. 首字采用首个用户可见内容，流式正常结束使用独立字段。
5. 先提交事实再推进游标，重读批次依靠唯一身份安全去重。
6. 统计输入只包含标准化事实；评分模块不得直接读取 New API 日志库。

## 6. sub2api 参考结论

参考仓库为 [`Wei-Shaw/sub2api`](https://github.com/Wei-Shaw/sub2api)，调研锁定提交 [`ab99d56e`](https://github.com/Wei-Shaw/sub2api/commit/ab99d56e9626e6cd731592dae8553c9758a0efa2)。可复用的设计思路包括：

- 成功请求和失败请求都保留请求编号、账号、模型及延迟证据。
- 首字排除只含用量的流式块，并识别缺少正常终止事件的截断流。
- 一次请求的多次上游错误保留尝试列表。
- 后台聚合回看最近窗口，允许迟到日志进入统计。

ManyRouter 不沿用以下口径：

- sub2api 部分聚合使用“实际费用大于零”代理成功，可能漏掉零价成功请求。
- 被动汇总只保留平台、分组和模型，账号及渠道归因在汇总中丢失。
- 错误日志没有统一渠道字段，也没有稳定的流式正常结束字段。
- 成功请求数去重后，用量和耗时仍可能按重复日志行累加。

因此 M2 独立实现采集合同和事实模型，不复制 sub2api 源码。该仓库声明 LGPL-3.0-or-later，同时中文 README 含“无商业授权”说明，复制代码前还需要单独确认授权边界。

## 7. 当前实现

截至 2026-09-05，本模块只完成设计归档。ManyRouter 尚无 New API 日志只读适配器、采集位置、请求事实、上游尝试事实、回填任务或采集接口。

M1 已保存站点、供应商、站点供应商关系及外部渠道编号，为 M2 的供应商归因提供基础。当前 New API 日志合同仍需通过源码、数据库样本和真实请求确认；架构文档记录的毫秒级总耗时补充也尚未实现。

## 8. 验证方式

实现时至少完成以下验证：

- 领域测试：首字定义、错误归属、请求与尝试归并、供应商映射和完整性判断。
- 适配合同测试：覆盖受支持 New API 版本的成功、失败、限流、重试、流式完成和流式截断样本。
- PostgreSQL 集成测试：批量追加、唯一去重、事务回滚、游标锁和历史更正。
- 任务测试：进程中断后重读、迟到记录回看、单站失败隔离和退避重试。
- 安全测试：只读权限，禁止访问基础表和敏感列，错误摘要不会保存密钥或正文。
- 真实验收：逐站抽样对比源日志与 ManyRouter 事实，覆盖重启续传、重复采集和一条带供应商切换的真实请求。

完成依据需要同时包含自动化测试、真实抽样结果、采集位置证据和可查询事实。只看到任务成功状态不能判定模块完成。
