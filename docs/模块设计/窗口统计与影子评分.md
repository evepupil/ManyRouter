# 窗口统计与影子评分模块设计

> 模块定位：把真实流量和主动测评事实汇总成带样本、可信度与算法版本的窗口统计，并生成不修改真实线路的评分与成员建议
> 对应代码：规划为 `internal/domain/scoring`、`internal/application/evaluation`、`internal/adapters/storage/postgres/scoring_*.go`、`internal/jobs/aggregation_*.go`、`internal/jobs/scoring_*.go`、`db/query/scoring*.sql`、`api/operations.yaml`（尚未实现）
> 所属里程碑：[M2 - 建立可信观测与影子评分](../roadmap.md#m2)
> 当前状态：进行中
> 最近更新时间：2026-09-05
> 架构依据：[统计与评分](../架构设计.md#86-统计与评分)、[统计维度](../架构设计.md#155-统计维度)、[评分与状态](../架构设计.md#17-评分与状态架构)、[历史数据](../技术设计.md#65-历史数据)

## 1. 职责与边界

本模块负责：

- 从[真实流量采集与测量事实](./真实流量采集与测量事实.md)和[主动测评与模型真实性](./主动测评与模型真实性.md)读取标准化事实。
- 生成一分钟统计事实、固定窗口汇总和不同评分周期的指标。
- 按站点、供应商、模型及其组合计算价格、延迟、SLA 和质量分项。
- 评估样本量、数据新鲜度、采集完整性和检测证据，给出可信度。
- 应用硬性排除条件，生成带完整原因的影子评分和成员调整建议。
- 保存算法、规则、输入窗口和结果版本，支持解释、比较与重算。

M2 不修改真实线路、分组、入口或价格。运营人员可以查看和采用建议，实际 Auto 自动调整属于 M3。用户请求过程中不调用本模块，控制台只读取已经保存的快照。

## 2. 结构与数据流

### 2.1 计划目录

| 位置 | 职责 |
|---|---|
| `internal/domain/scoring/` | 窗口、样本、可信度、硬门槛、分项和综合分纯规则 |
| `internal/application/evaluation/` | 组织聚合、生成快照和影子建议 |
| `internal/adapters/storage/postgres/scoring_*.go` | 分钟事实、固定汇总、规则版本、快照与建议存储 |
| `internal/jobs/aggregation_*.go` | 增量聚合、回看重算、回填和保留策略 |
| `internal/jobs/scoring_*.go` | 周期评分、异常触发和建议刷新 |
| `db/query/scoring*.sql` | 聚合读取、幂等写入和快照查询 |
| `internal/transport/http/`、`api/operations.yaml` | 运营统计、评分解释和影子建议接口 |
| `web/src/features/` | M2 统计、评分和建议页面；实现时按现有 Token 与基础组件拆分 |

### 2.2 数据流

```text
不可修改的测量事实
    -> 按来源、站点、供应商和模型生成一分钟事实
    -> 汇总到固定时间桶及延迟直方图
    -> 组合近期窗口并检查采集覆盖与样本
    -> 应用凭证、余额、连续失败和真实性硬门槛
    -> 计算价格、延迟、SLA、质量分项
    -> 生成带算法版本的评分快照
    -> 为每个站点和固定 Auto 生成影子成员建议
    -> 运营人员查看，不自动下发
```

聚合和评分任务分别运行。新日志到达只更新受影响时间桶，再由评分任务读取完整统计；控制台查询不扫描 New API 原始日志。

## 3. 窗口统计

### 3.1 统计层次

| 层次 | 粒度 | 用途 |
|---|---|---|
| 测量事实 | 单次用户请求和单次上游尝试 | 审计、重算和问题定位 |
| 分钟事实 | 1 分钟 | 近期变化、迟到数据回算和固定汇总来源 |
| 固定汇总 | 5 分钟、1 小时、12 小时、1 天 | 24 小时、7 天、30 天查询及趋势 |
| 评分窗口 | 15 分钟、1 小时、24 小时 | 近期异常、当前表现和稳定基线 |
| 观察窗口 | 7 天、30 天 | 恢复速度、价格稳定性和长期趋势 |

一分钟事实至少保存成功、失败、有效请求、各错误分类、输入输出用量、首字和总耗时的总和、样本数及直方图。固定汇总只相加计数、总和和直方图桶，不能平均已有百分位。

正常聚合持续回算最近 10 分钟，吸收迟到事实。历史回填使用独立任务和进度，不影响近期任务。M2 初始规模保留原始测量事实，不启用自动删除；上线前根据真实增长量另行确定归档周期。

### 3.2 统计维度

M2 至少支持：

- 全局供应商与供应商模型。
- 站点、站点供应商和站点供应商模型。
- 站点固定 Auto 与模型。
- 数据来源、时间窗口和错误分类。

真实流量与主动测评分别保存请求量、成功率和延迟。需要组合时按规则读取两类统计并展示各自贡献，不能先混合原始请求后计算一个无法解释的结果。

### 3.3 请求和尝试口径

| 指标 | 数据对象 | 含义 |
|---|---|---|
| 用户最终成功率 | 用户请求事实 | 用户最终获得正常结果的比例 |
| 供应商尝试成功率 | 上游尝试事实 | 该供应商被调用后完成尝试的比例 |
| 切换恢复率 | 用户请求及其尝试链 | 前一次失败后由其他供应商完成的比例 |
| 限流率 | 供应商负责的尝试 | 上游限流次数占有效尝试比例 |
| 首字和总耗时 | 有明确计时与终止证据的样本 | P50、P90、P95、平均值和样本量 |
| 流式完整率 | 已开始流式输出的请求或尝试 | 正常终止占比 |

用户参数错误、用户密钥错误和用户主动取消不进入供应商 SLA 分母。供应商鉴权、余额、限流、超时、上游错误、传输中断和不完整流按照错误归属进入对应分项。站点自身故障进入站点局部结论，不能污染供应商全局结论。

### 3.4 延迟直方图

首字和总耗时使用统一毫秒区间：`50、100、250、500、1000、2000、3000、5000、8000、10000、15000、30000、60000、120000、300000、600000、+Inf`。

P50、P90 和 P95 从合并后的直方图计算，同时返回样本数和区间误差。平均值由总和除以有效样本数。首字只统计流式且产生可见内容的请求；总耗时同时按成功和失败分别统计，综合展示不能隐藏失败请求的长尾。

## 4. 数据可信度

每个分项同时生成可信度，至少考虑：

- 样本量是否达到该规则的最低要求。
- 最近样本距当前时间多久。
- 站点采集是否追上源端，以及窗口内是否存在缺口。
- 有效计时、错误归属和供应商映射的完整比例。
- 真实流量与主动测评各自的覆盖情况。
- 模型真实性是否拥有可信参考和稳定复测。

可信度取参与因素中的最低等级，避免大量旧数据掩盖当前采集中断。结果使用“高、中、低、证据不足”四档，并保留每项原始样本数和缺口原因。

样本不足时仍可展示统计值，但不生成确定的准入或退出建议。默认最低有效样本为 50 个，作为首轮影子基线保存到规则版本中；主动测评和真实性检测使用各自样本门槛。该默认值需要用 M2 真实数据校准，不构成对外 SLA 承诺。

## 5. 评分规则

### 5.1 硬性排除

以下条件先于综合分执行：

- 模型真实性结论为“不一致”。
- 供应商访问凭证确认无效。
- 余额耗尽或确认不能继续服务。
- 连续供应商负责失败达到规则门槛。
- 运营人员确认重大风险仍有效。

M2 只在快照中标记“建议排除”及原因。真实成员保持不变，紧急人工停用继续使用 M1 能力。

### 5.2 四项分数

所有分项归一为 0 至 100，并保存原始指标和计算说明：

| 分项 | 首期输入 |
|---|---|
| 价格 | 当前采购成本、候选间相对成本、近期价格变动次数和幅度 |
| 延迟 | 首字 P50/P95、总耗时 P50/P95、波动及有效样本 |
| SLA | 供应商尝试成功率、限流率、连续失败、流式完整率、恢复时间和容量稳定性 |
| 质量 | 模型真实性结论、业务题得分、稳定性和证据可信度 |

阈值、归一化方式、缺失值处理和分项权重全部属于评分规则版本。缺失分项不自动获得满分；证据不足时降低可信度，并按策略选择继续观察或排除。

### 5.3 近期权重

首版影子规则将 15 分钟、1 小时、24 小时窗口按 50%、30%、20%组合，使近期变化更快影响结果，7 天和 30 天只用于趋势、价格稳定性和恢复判断。某个短窗口样本不足时，在仍有完整数据的窗口之间重新分配权重，同时降低最终可信度。

连续异常采用独立计数，不能被长期平均值稀释。恢复需要连续多个合格窗口，准入线与退出线分开，避免短时间反复进出。

### 5.4 固定 Auto 影子建议

M2 为最低价、低延迟、高 SLA、高质量和均衡五类固定 Auto 读取同一四项分数，再应用各自带版本的权重与门槛。每条建议至少包含：

- 站点、Auto、模型和候选供应商。
- 当前真实成员与建议成员。
- 建议加入、保留、退出或观察。
- 四项原始指标、分数、可信度、硬门槛和原因。
- 使用的事实截止时间、统计窗口、评分规则版本和建议版本。
- 与上一建议相比的变化及仍需连续确认的窗口数。

建议页面只提供查看和人工采纳入口。M2 不创建线路方案，不调用 New API；M3 才能把合格建议交给正式策略调整。

## 6. 版本与重算

- 一分钟事实和固定汇总按“维度 + 时间桶 + 聚合版本”唯一，回算时原子替换受影响桶。
- 错误分类、直方图区间、评分规则和固定 Auto 权重分别带版本。
- 每份评分快照记录输入数据截止时间、覆盖状态、样本数和全部规则版本。
- 新算法生成新快照，旧快照保留，禁止覆盖历史分数。
- 影子建议引用确定的评分快照；重算结果不能回写旧建议。
- 任务重复执行时，内容相同的输入和版本得到同一业务结果，不产生重复建议。

## 7. sub2api 参考结论

[`sub2api Channel Monitor V2`](https://github.com/Wei-Shaw/sub2api/blob/ab99d56e9626e6cd731592dae8553c9758a0efa2/backend/internal/repository/channel_monitor_v2_aggregation.go#L166-L238)已经采用一分钟事实、固定窗口汇总、延迟直方图、样本门槛、错误分类版本和覆盖游标。M2 复用这些工程思路，并保留其“忽略错误分类后仍展示真实失败量”的做法。

ManyRouter 需要补齐以下差异：

- 汇总维度必须保留供应商和站点供应商，分组不能代替供应商。
- 成功使用明确结果，不能以费用大于零判断。
- 请求最终结果与每次供应商尝试分别聚合。
- 主动数据与真实流量同时存在且来源分开。
- 流式完整率、失败耗时、采集缺口和可信度进入结果。
- 长窗口从合并后的直方图计算百分位，禁止平均各小窗口的百分位。

sub2api 的通用健康分混合业务错误、首字和系统资源，更适合单个中转站运维。ManyRouter 的四项分数面向跨供应商比较，数据库和任务节点健康单独监控，不进入供应商质量分。

## 8. 关键决策

1. 一分钟事实是所有窗口的统一来源，固定汇总相加计数和直方图。
2. 请求结果与尝试结果分开统计，避免成功切换掩盖供应商故障。
3. 每个分数同时给出样本、截止时间、覆盖缺口和可信度。
4. 硬性门槛先于综合评分，价格低不能抵消凭证、余额或真实性问题。
5. 近期窗口权重更高，连续失败和恢复另行判断。
6. M2 只写影子快照和建议，真实线路保持人工控制。

## 9. 当前实现

截至 2026-09-05，本模块只完成设计归档。ManyRouter 尚无分钟统计、固定窗口汇总、错误分类、可信度、评分规则、快照、影子建议接口或页面。

M1 已提供供应商采购价格、站点供应商关系、固定 Auto 人工成员、价格版本和同步结果，可作为 M2 评分维度及建议对照。当前没有真实测量事实，任何供应商分数或建议都不能视为已验证结果。

## 10. 验证方式

实现时至少完成以下验证：

- 纯规则测试：错误分母、请求与尝试口径、直方图百分位、窗口权重、可信度、硬门槛和防抖。
- PostgreSQL 集成测试：分钟事实、固定汇总、最近窗口回算、迟到数据、版本并存和重复任务。
- 一致性测试：固定汇总与同范围原始事实抽样对账，计数、用量和直方图桶一致。
- 评分测试：冻结语料和固定规则下结果可重现，修改规则后生成新版本且旧结果不变。
- 缺口测试：采集落后、站点离线、待归因和样本不足不会显示满分或确定建议。
- 隔离测试：一个站点的数据和故障不改变另一站点局部统计；供应商全局结论只使用允许共享的事实。
- 影子验收：生成五类固定 Auto 建议后，核对 New API 渠道、分组、入口和价格完全未被修改。
- 人工抽样：从两个独立 New API 实例抽取请求，与一分钟统计和最终评分解释逐项核对。

M2 完成需要日志采集对账、主动测评结果、真实性结论、窗口统计和影子建议全部可查，并证明未修改真实线路。
