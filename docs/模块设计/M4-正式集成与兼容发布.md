# M4 正式集成与兼容发布

> 模块定位：完成 ManyRouter 与受支持 New API 版本的正式接入、能力检查、批量配置同步和组合发布，验证 M3 用户侧能力在正式版本中的可用性。
> 对应代码：尚未创建；计划目录：`internal/adapters/gateway/`、`internal/compatibility/`、`internal/release/`、`deploy/` 及 New API 适配仓库。
> 所属 M 里程碑：[M4：完成正式集成与可复制发布](../roadmap.md#m4)
> 当前状态：未开始
> 最近更新时间：2026-09-04
> 架构依据：[架构设计](../架构设计.md)
> 技术依据：[技术设计](../技术设计.md)

## 1. 职责与边界

本模块负责把已经在 M0～M3 验证过的 ManyRouter 管理能力整理为正式的站点接入和发布能力，重点包括：

- 检查目标 New API 实例是否具备当前组合所需的能力。
- 通过 New API 的正式窄权限接入端点，整批同步受管渠道、分组、倍率、状态和可见配置。
- 维护 ManyRouter 与 New API 版本之间的兼容矩阵、推荐组合和已知限制。
- 固定 ManyRouter、New API、数据库和迁移版本的组合发布。
- 验证升级、失败处理和回退过程。
- 对 M3 已交付的用户侧价格、可用供应商数量、SLA、延迟、质量及更新时间展示进行正式发布验证。

本模块不负责首次实现用户侧页面和用户数据代理；这些能力属于 M3。本模块也不接管 New API 的用户、余额、订单、计费、协议转换和请求转发，不直接读写 New API 业务主库或日志库。

## 2. 结构与数据流

### 2.1 正式同步链路

```text
ManyRouter 期望状态
        │
        ▼
New API 能力检查
        │
        ├─ 不满足：进入只读状态并告警
        └─ 满足
             │
             ▼
       窄权限整批同步
             │
             ▼
       New API 刷新运行状态
             │
             ▼
       ManyRouter 重新读取并核对
             │
             ├─ 一致：记录已确认状态
             └─ 有差异：重试、告警或回退
```

整批同步只允许操作已经由 ManyRouter 创建或明确接管的资源。写入结果需要经过重新读取核对，接口接受请求不能单独作为同步成功依据。

### 2.2 版本与组合发布链路

```text
ManyRouter 版本 + New API 版本
              │
              ▼
        兼容能力验证
              │
              ▼
        组合清单与推荐版本
              │
              ▼
          站点部署或升级
              │
       ┌──────┴──────┐
       ▼             ▼
    验证成功       验证失败
       │             │
    标记生效      恢复上一组合
```

每个站点使用已经通过验证的组合。组合发布同时覆盖 ManyRouter、New API、PostgreSQL 和数据库迁移的版本关系，生产环境不以浮动的 `latest` 作为依据。

### 2.3 M3 用户能力的发布验证

验证从 New API 用户页面进入，通过 New API 同源后端代理访问 ManyRouter 用户数据服务，确认用户能看到：

- 当前价格。
- 可用供应商数量。
- SLA、延迟和质量信息。
- 统计更新时间及数据不足、观察中或近期异常等状态。

验证还需确认 ManyRouter 暂时不可用时，用户页面可以说明数据暂时无法更新，已有 New API 模型请求仍能继续。

## 3. 关键决策

- ManyRouter 核心通过稳定的网关适配能力对接 New API，版本差异收敛在适配层。
- 正式版本使用 New API 增加的窄权限整批接入端点；早期逐项 HTTP 管理接口属于 M0 的过渡方式。
- 能力检查依据实际能力响应和合同测试，不只比较版本字符串。
- New API 业务主库保持隔离，配置写入统一通过 New API 业务接口完成。
- New API 的人工安全停用优先于自动恢复，非受管资源不得被同步。
- 同步采用最终一致：保存期望状态，执行后重新读取并核对；失败时继续使用上一次已确认配置。
- 生产站点只执行人工发起的升级；升级失败必须能够恢复到上一份已验证组合。
- 多站点使用同一份经过验证的 ManyRouter 与 New API 组合，站点配置和运行数据仍按站点隔离。

## 4. 当前实现

ManyRouter 工程尚未创建，本模块暂无实现。当前仓库中的 New API 源码仅作为分析和适配基线，尚未形成正式适配仓库、窄权限整批端点、兼容矩阵或可发布组合。

M3 用户侧能力也尚未进入可运行的 ManyRouter/New API 组合，因此本阶段只记录其正式发布验证范围，不把设计文档视为已完成能力。

## 5. 验证方式

- 使用真实 New API 进程和数据库验证能力检查、整批同步、缓存刷新、重新读取和配置核对。
- 验证重复执行同一操作不会创建重复渠道、分组或产生错误的状态变化。
- 验证只允许修改受管资源，ManyRouter 无法写入 New API 业务主库和日志库。
- 为声明支持的 New API 版本运行真实兼容合同测试，并记录已验证能力、限制和推荐组合。
- 在干净环境从零部署一个新站，验证组合清单、站点注册、日志采集、真实调用、计费和故障切换链路。
- 执行升级验证，确认升级前组合和配置可以恢复，失败时 New API 按上一份已确认配置继续服务。
- 验证 M3 用户侧页面的价格、供应商数量、SLA、延迟、质量和更新时间展示，以及 ManyRouter 暂时不可用时的页面降级。
- 通过格式化、静态检查、后端单元测试、数据库集成测试、前端类型检查、前端构建和兼容测试等项目门禁。

## 6. 待扩展项

- 支持更多经过验证的 New API 版本和其他网关适配器。
- 在确有需求时增加更细的升级编排、灰度发布和站点分批发布能力。
- 根据真实运营规模拆分独立的兼容验证、发布和站点执行能力。
- 与更多通知渠道和外部发布系统集成。

这些扩展不得改变用户请求不依赖 ManyRouter 实时在线、配置写入经过 New API 业务接口以及非受管资源不被修改的边界。
